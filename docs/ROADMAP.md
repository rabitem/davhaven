# Roadmap

Davhaven 1.0 is the scope of [`PLAN.md`](PLAN.md) section 1.1. Everything not in 1.0 is listed here with the
reason; nothing is dropped silently. An item moves into a release through a change to the plan. If you want to work
on one, open an issue first.

## Scope of 1.0

Davhaven has not been released yet; this is the set of features the first release is meant to contain.

CalDAV core with sync-collection, server-side scheduling, CalendarServer sharing, notifications, principal
search and extended MKCOL; VEVENT/VTODO/VJOURNAL storage; internal delivery, iMIP REQUEST/CANCEL/REPLY, the RSVP
page, inbound iTIP (off by default), resource auto-accept and free-busy; app passwords, API, feed and RSVP
tokens; feeds; the management API; the MCP server; Google and Microsoft pull import behind cargo features and
disabled in configuration; the `ContentScanner` port; the in-process rate limiter.

## Backlog

| Area | Item | Reason it is not in 1.0 |
| --- | --- | --- |
| CalDAV | Managed attachments (RFC 8607) | Needs blob storage, quotas and scanning; inline binary `ATTACH` up to 256 KiB covers 1.0. |
| CalDAV | Per-user alarm overlay | Changes the ETag and change-log model; 1.0 shares alarms and accepts acknowledge/snooze-only writes from read-only bindings without storing them ([ADR-0004](adr/0004-shared-alarms.md)). |
| CalDAV | Properties of the home and the inbox (`schedule-default-calendar-URL`, default alarms) | The data model keeps properties per calendar and per binding only; a `PROPPATCH` of the home or the inbox is refused (403) and clients carry on. Invitations are added by the scheduling policy. |
| CalDAV | `calendar-query` on the scheduling inbox (RFC 6638 section 2.3) | Clients that poll the inbox (Apple Calendar, Thunderbird) use `sync-collection` and `calendar-multiget`, which are implemented; a filter over iTIP messages needs the inbox listing to carry parsed messages. The report is refused with 403 `DAV:supported-report` meanwhile. |
| CalDAV | Path-addressed variants of the calls that take only the name of the home owner (`SchedulingService::outbox_post`, `inbox_list`, `SharingService::list_notifications`) | The DAV layer resolves the resource first (one more transaction and authorization load per outbox `POST` and per listing) so that the tenant of the path is judged before the name reaches the service (R4, tests in `protocol/collaboration.rs` and `crates/it`). The variants (`…_at(ctx, &ResourcePath, …)`, resolving with `resolve_home`) would be additive methods of the sharing and scheduling services. |
| CalDAV | Cursor pages and a limit for `SharingService::list_notifications`, `SchedulingService::inbox_list` and their repositories | A principal's notification collection is read whole (the response is bounded when it is written, not when it is read); the amplification is bounded by `limits.dav.max_sharees_per_request`. Additive `limit`/cursor parameters and a retention rule for notifications are a change of the storage contract. |
| CalDAV | `SchedulingService::inbox_delete_if` | The conditions of an inbox `DELETE` are evaluated by the DAV layer before the removal, which is atomic enough for items that the store never rewrites (`docs/interop.md`); a service-side check would be an additive method of the inbox service. |
| CalDAV | WebDAV `LOCK` (class 2) | Not required by the supported clients; conditional requests and Schedule-Tag cover concurrent edits. |
| Scheduling | Group address expansion | Attendees with `CUTYPE=GROUP` get `SCHEDULE-STATUS` 3.7 in 1.0; expansion needs membership snapshots and fan-out limits. |
| Providers | Push direction (Davhaven → Google/Microsoft) | 1.0 imports only (pull into mirror calendars); the outbox kind `provider_push` is reserved. |
| Providers | Incremental pulls (Google `syncToken`, Microsoft delta queries) | Both adapters list the window of the calendar on every pull and let the sync engine find what changed (content hashes make an unchanged event a no-op), which costs a request per page of events per pull and keeps no state of the provider in step; the port already carries deltas (`RemoteChanges::delta`) and the engine applies them. |
| Providers | More than the primary calendar of an account; tasks, birthdays, attendees, organizers and alarms | A mirror is one calendar of events, read-only and without scheduling, so that nothing it holds can mail anybody; each of these changes what a mirror is. |
| Providers | Per-tenant OAuth clients | One OAuth client per provider serves the deployment (`[providers.<name>]`); a tenant that needs its own client needs its credentials in tenant data and a redirect per tenant. |
| Providers | Finding the due accounts with one query across tenants | The sync worker reads the accounts of every active tenant, one transaction per tenant, every poll interval, so the cost grows with the number of tenants and not with the number of accounts (R14). A system-scope query (enabled providers, status not `disabled`, ordered by due time, with a limit) needs the due time as a column of its own, which is a schema change. This is fine for the number of tenants of a 1.0 deployment. |
| Providers | Accounts identified by an immutable id | An account is matched on the address the provider names (`account_ref`: the primary calendar id at Google, the mail or user principal name at Microsoft), which can change when a mailbox is renamed: the person then gets a second account and mirror instead of a reconnection. The Graph `id` with the tenant, or the OpenID `sub` at Google, would be stable; a unique key on (tenant, principal, provider, account) would also stop two concurrent callbacks from creating two accounts. Needs a column and an index. |
| Providers | Complete `VTIMEZONE` components in mirror objects | The Google objects carry `TZID` parameters without a definition ([`interop.md`](interop.md)), as the provider sends them. Rendering one component per zone for the window (the feed renderer does) is possible, but a recurring series needs observances for ever. |
| Providers | `last_sync_at`, `next_sync_at` and the reason as a field of `ExternalAccountView` | The reason of a failure reaches API clients as the start of `last_error` (`auth_revoked: …`), and nothing says whether a mirror is current. Additive optional fields of the wire type and a regenerated `openapi.json` would show it. |
| Providers | One switch and one catalog for the providers | A provider is available when `plugins.providers` selects it **and** `[providers.<name>] enabled` is true, and `crates/app` lists the providers the project ships (`KNOWN_PROVIDERS`) for a build that lacks them. The server could build the catalog from the registry and the configuration, with selection as the only switch, and the window of the import (`history_days`, `future_days`) could move into the engine's settings and be passed to the adapters. Changes `AppDeps`, `Provider::enabled` and the contract of the provider list. |
| Providers | A distinct signal for a refused access token | The engine renews the access token and repeats the call for every `Rejected` of the calendar API, so a `404` or `403` costs one extra refresh. A kind of its own for `401` (an additive `PortErrorKind`) would limit renewal to authentication failures. |
| Providers | The tokens of a deleted principal revoked at the deletion | They are revoked when the sync worker claims the account next (and only while its provider is on), not in the transaction that deletes the principal. |
| Web | A web channel for the unauthenticated OAuth callback | The callback reaches the application with the internal context (`Channel::Internal`), which authorization treats as trusted server work; only `ctx.locale` is read there today. An anonymous context on its own channel (and the `Accept-Language` of the visitor) is a change of `davhaven-domain`. |
| Auth | Token introspection authenticator | External identity providers are not needed for 1.0; the `Authenticator` chain accepts such an adapter later without contract changes. |
| Auth | On-behalf-of delegation | Rejected for 1.0 because of the impersonation risk; principal tokens act only as their principal. |
| MCP | OAuth for MCP (authorization server metadata, dynamic client registration) | 1.0 uses static principal tokens with `mcp:*` scopes and an expiry (`docs/interop.md`); an OAuth front end is an authenticator plus metadata endpoints and changes no tool. |
| MCP | Browser clients (CORS for `mcp.allowed_origins`) | The origin check is the defense the specification requires; a preflight needs an `OPTIONS` path without credentials. Assistants that run in a browser use their back end. |
| MCP | Other protocol revisions (`2024-11-05`, `2025-03-26`, `2025-11-25`, the per-request lifecycle of `2026-07-28`), prompts and resources | The plan fixes revision `2025-06-18` and tools only; `initialize` is answered with it whatever the client asks for, and the client decides whether to go on. |
| MCP | What scheduling did, in the result of a write | `create_event` and `update_event` return the event only; whether invitations were mailed or queued (`ScheduleOutcome`) is not part of the tool output. An additive field of `wire::mcp` would show it. |
| Scanning | ClamAV adapter | Only useful once managed attachments exist; the `ContentScanner` set is empty by default. |
| Rate limiting | Shared limiter (`ratelimit-postgres`) | 1.0 runs as a single instance per database unless a shared limiter is configured; the outbox and workers are already multi-instance safe. |
| Rate limiting | Scheduling quotas behind the `RateLimiter` port | The quotas of external recipients per organizer and hour and per tenant and day (`scheduling.external_per_organizer_per_hour`, `external_per_tenant_per_day`) are counted in the memory of the process, because the port owns its rates in the configuration of the adapter and these limits are the `[scheduling]` settings; a deployment with several instances counts per instance until the shared limiter exists and the port takes the allowance as an argument (a contract change). The inbound iTIP buckets (`itip_inbound`, `itip_inbound_gateway`) already go through the port. |
| Operations | Metrics labelled with the tenant (`observability.metrics.tenant_label`) | The plan lists it; the key is reserved and **refused when set to `true`** (`config check` fails with this reason) until it works: the metrics are recorded where the work happens, and the tenant is not known there without threading it through every adapter call; label cardinality needs a decision per deployment. The plan text still has to be updated to say so. |
| Operations | OTLP over TLS | The exporter speaks plain gRPC to a collector on the local network, which is the deployment the contract describes; TLS to a remote backend needs a trust-root setting (system roots or a bundle) and more dependencies in the exporter, and a collector carries the traffic onwards with TLS anyway. |
| Operations | Database pool metrics (`db_pool_in_use`, `db_pool_waiting`) | The plan lists them. The pool belongs to the PostgreSQL adapter, which does not export them; sqlx offers the pool size and the idle count but no waiter count, so `in_use` can come from the adapter (a gauge set from `observe`) and `waiting` needs a counter of its own around `acquire`. The runbook points at the database side meanwhile. The plan text still has to be updated to say so. |
| Auth | The first administration token of a tenant needs a shell on the host | Only `davhaven admin bootstrap` mints it, so the ephemeral tenants of the staging run (`docs/testing.md`) cannot be made by a pipeline that reaches the instance over HTTP only: the operator prepares both tenants and hands over their tokens. **Open question**: for example let a system token create a tenant together with its initial administration token, returned once and not replayable; the runner would then make and delete its tenants itself. |
| Auth | Principal tokens never administer, `searchCalendars` included | The oracle (`[[admin_actor]]` of `crates/testkit/matrix/expectations.toml`) has principals refused on every administration operation whatever scopes their token carries, including a principal token that carries `calendars:read` on the search for calendars, which a tenant token with that scope may use. The server does this today; the plan does not say it in these words. **Open question**: record the rule in the plan, or change the oracle and the server together. |
| Quality | Per-state RSVP token cases of the staging run and a scheduling matrix over a deployed instance | A deployed instance redirects its mail, so the mails a case looks at, the event sinks and the inbound gateway are not observable from outside; the scheduling matrix runs in process and the staging run covers the flows that need no capture of mail. |
| CalDAV | The change log of the home collection (`CollectionKind::Home`, `principals_sync.home_seq`, the home branch of `ObjectService::sync`) | The stores write a change for every binding change and the application answers a sync of a home path, but no protocol serves it: DAV answers `sync-collection` of a home with 403 `DAV:supported-report` and shows neither `DAV:sync-token` nor `CS:getctag` for it, and the changes feed of the API is per calendar. It is kept because removing it changes the service contract and the storage; a protocol that wants it (a home-level `sync-collection` for clients that watch the list of calendars) can serve it without a store change. |
| Quality | Coverage gate on pull request diffs | CI time; 1.0 enforces ratcheted per-crate floors on `main` and nightly. |
| Documentation | `docs/problems.md`, the problem catalog with the answers of the principal `PUT` (`name-reserved`, `external-ref-reserved`, `address-reserved`) | The generator behind `xtask problems-docs` is not registered, so the page does not exist yet. The answers are documented in the OpenAPI document (`putPrincipal`, the 409 and 412 components), `docs/api.md`, `docs/interop.md` and ADR-0015, and the rows are in `wire::ProblemCode`. |

## Non-goals for 1.0

CardDAV, an inbound SMTP server (the inbound iTIP HTTP endpoint covers mail gateways), a web calendar UI,
WebDAV `LOCK`, RFC 3744 ACL writes.
