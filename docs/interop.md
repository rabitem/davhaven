# Interoperability notes

Where Davhaven deviates from an RFC, makes a choice the RFCs leave open, or depends on how other systems behave,
it is written down here (`ENGINEERING_RULES` R7). The first section covers iCalendar storage and iTIP processing
(`docs/ical.md` describes that behaviour in full); the others follow the protocols and surfaces of the server.

## iCalendar storage and CalDAV data (RFC 4791, RFC 5545)

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| Stored bytes | the client's bytes, verbatim; the server serializes only what it changes itself | Clients compare what they read with what they wrote; unknown properties and vendor parameters must survive. |
| Line endings, folding, byte order mark | `CRLF`, bare `LF` and bare `CR` are accepted, a leading BOM is ignored | Some clients and exporters send `LF`. |
| Windows time zone names | `TZID=W. Europe Standard Time` resolves to an IANA zone through the embedded CLDR table, with or without a `VTIMEZONE` | Outlook and CalDav Synchronizer write them. |
| Unknown `TZID` without a usable `VTIMEZONE` | the value is read as floating time | Refusing the object would lose the client's data; RFC 5545 asks for a definition but clients omit it. |
| Zero-length events | `DTEND` equal to `DTSTART` is accepted; `time-range` follows the strict row of the RFC 4791 section 9.9 table for it and the inclusive row for `DURATION:PT0S` or no end. A date-valued `DTEND` equal to `DTSTART` is one day | Real clients write all three forms, and a query for a day starts at midnight. |
| `RRULE:FREQ=HOURLY` | accepted with a `COUNT` or an `UNTIL`; `SECONDLY` and `MINUTELY` are refused (PLAN 2.15). A rule without an end must reach the year 2100 within `max_iterator_steps` when the object is stored, otherwise `max-instances`: an endless hourly rule never does | A stored object must never make a later `REPORT` fail. |
| `EXRULE` | kept, ignored when expanding | RFC 5545 obsoleted it; refusing would lose data. |
| `METHOD` in a stored object | refused with `valid-calendar-object-resource` | RFC 4791 section 5.3.2.1. Calendar exports of Google and others carry `METHOD:PUBLISH`; the client has to strip it. |
| Preconditions of invalid objects | restrictions of a calendar object resource (`METHOD`, mixed component types, several UIDs, duplicate `RECURRENCE-ID`) are `valid-calendar-object-resource`, differing organizers `same-organizer-in-all-components`, the rest `valid-calendar-data` | The elements RFC 4791 and RFC 6638 define, which CalDAV test suites assert. |
| Preconditions of queries | an invalid filter, a time range outside 1900-2100 or longer than ten years and too many instances in an expansion are `valid-filter`; `min-date-time`, `max-date-time` and `max-instances` are only answered for a `PUT` | RFC 4791 defines them for `PUT` only. |
| Running out of time | 503 with `Retry-After`, never a statement about the data | It depends on the load of the machine. |
| Data the writer cannot reproduce | what `parse::accept` lets in (the gate of `PUT`, a batch item, a JSON merge, an iTIP message and a `calendar-timezone`) is written by `serialize` as text that parses to the same calendar and the same content hash, within the same limits: data whose written form is longer than `max_value_length` or `max_resource_size` is refused when it comes in (escaping makes a `,` or `;` that came without a backslash two characters, and the server must be able to store its own text). The reader of the parser library is more lenient than its writer, and data for which the two disagree is refused as `valid-calendar-data` instead of being read in another way: a parameter name with a backslash, a quote or a colon in it, a UTC offset of fewer than four digits (`TZOFFSETTO:+2`), a date-time that something follows (`DTSTAMP:20270101T000000Z2`, `DTSTART:20270301T100000+0100`: a client writes `Z` or a `TZID`) and a parameter value that has a quote in it. Unicode white space other than the space and the tab is no blank around a name. The stored bytes stay the client's. What is already stored is read with `parse`, which does not decide acceptance again: a `calendar-query`, a feed, a search or a free-busy answer never fails because of how a client wrote a value. An object that `parse::accept` would refuse cannot be rewritten by the server (a JSON merge, a `SCHEDULE-STATUS` or `PARTSTAT` merge is refused as `valid-calendar-data`, as is a client's own write of the same bytes) | Everything that writes a stored object after changing it (JSON merges, `SCHEDULE-STATUS`, iTIP) goes through the writer: an object that does not survive it cannot be changed, and its content hash would depend on how often it went through. Covered by the fuzz target `parse_validate` and the robustness test; the corpus and every client body of the test suite pass the gate. |
| Floating times and all-day dates | read in the calendar's `CALDAV:calendar-timezone` (`tz::calendar_timezone` validates and resolves it); a `VTIMEZONE` that cannot be named (observances only, no known `TZID` or location hint) is refused as a calendar time zone | RFC 4791 section 9.9. A zone the server cannot name cannot be given to the expansion code. |
| Index pre-filter | `first_start` and `last_end` are widened by one second, floating values by 14 hours | RFC 4791 section 9.9 compares inclusively in some rows, the store compares strictly. |
| `RANGE=THISANDFUTURE` | expanded when reading (the following instances move and reshape), never written | RFC 5545 allows it, few clients evaluate it: after a write that used it, the server would show reshaped instances where the clients still show the old time. |
| "This and following" edits through the API and MCP | the series is cut with an `UNTIL` and the edited instance starts a new series with a UID of its own (`merge_event_split`); two objects result | The form clients understand. The new series is a new scheduling object; whether its attendees are told is the application's decision. |
| `EMAIL` alarms in JSON writes | refused | RFC 5545 section 3.6.6 needs a `SUMMARY` and `ATTENDEE`s the event model does not carry. |
| Busy-only feeds | only timing properties stay, with the parameters that say how to read them; `VTIMEZONE`s are rebuilt from their identifier and the timing of their observances; the UID is an HMAC keyed by the application | A name, comment or `X-` property of a client must not reach a public feed. |
| Corpus | the files of `testdata/corpus` are reconstructions of what the clients send, written for this repository; the client-flow grid keeps reporting the cells that rest on them as synthetic | PLAN 3.5 asks for captures. They replace the reconstructions as the capture middleware (`observability.dav_capture`) produces them. |

## WebDAV and CalDAV core (RFC 4918, RFC 4791, RFC 5689, RFC 6578)

The behavior of the DAV methods, properties and reports of `davhaven-dav`. Sharing requests, the scheduling inbox and
outbox, notifications and principal search are described in "Collaboration over DAV" below.

### Discovery and capabilities

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| `DAV` header | `1, 3, calendar-access, calendar-auto-schedule, extended-mkcol, calendarserver-sharing, calendarserver-principal-search`; no class 2, so `supportedlock` and `lockdiscovery` are empty and `LOCK` and `UNLOCK` answer 405 | Locking is a non-goal (PLAN 1); conditional requests and `Schedule-Tag` cover concurrent edits. A service of the application that is not there (`unsupported`) answers 501 for the feature that needs it. |
| `OPTIONS` | answered without credentials, with `Allow` for the resource and the `DAV` header | Clients ask what the server can do before they log in. |
| `/.well-known/caldav` | 301 to `/dav/` for every method, without credentials; the target comes from `PublicUrls`, never from `Host` | RFC 6764. |
| Principal discovery | `PROPFIND /dav/` answers `current-user-principal` for the authenticated principal; `principal-collection-set` of every resource is `/dav/`. The principal is asked of the application only when the request names `current-user-principal` (or `principal-URL` of the entry point, or `propname`); a service that cannot tell leaves the one property 404 instead of failing the answer | The chain every client runs: entry point, principal, calendar home, calendars. The application finds the principal of a request (`PrincipalService::current`), because the context carries ids and the URL needs names. |
| Hrefs | path-absolute, percent-encoded by one encoder (`ResourcePath::format`), never absolute URLs. `Destination` accepts a path or an absolute URL whose authority is the configured DAV base or the `Host` of the request | A client must be able to compare hrefs byte for byte; an absolute `Destination` on another host is not ours to move to. |
| Unknown and foreign resources | a path that names no resource and calendars the caller cannot see (those of other users of the tenant included) are 404 with an empty body, **also** when the request would be refused for a reason of its own: a protected property, an invalid value, a value that is too large or too many dead properties in a `PROPPATCH`, `MKCALENDAR` or `MKCOL`, a multiget that names nothing. **Deviation:** a request whose path names *another tenant* is answered by the edge with 401 (and the challenge of that tenant), not 404: the tenant of the path is the hint of the login (`davhaven_http::tenant_hint`), and a credential of another tenant fails against it like an unknown credential (PLAN 2.6 and R4 ask for 404; the matrix expectation for the other-tenant actor has to say 401 until the edge resolves the tenant of a full login `name@login_domain` from the login domain and the services answer 404). What a request can name in a header or a body (the `Destination` of `MOVE` and `COPY`, the hrefs of a multiget) is judged by the services and is 404 for another tenant, like any invisible resource | PLAN 2.6: invisible is not forbidden; the 401 is the behavior of the shared edge. |
| Methods a resource does not define | 405 with `Allow`; `GET` of a collection, `PUT` of a collection and `POST` of an object are examples. Every 405 carries `Allow`, also the one for `MKCALENDAR` on an existing resource | The method table (`allowed_methods`) is the contract between the dispatcher and the handlers; RFC 9110 section 15.5.6. |
| What comes before visibility | only refusals that look at the shape of the request alone and are the same for every resource: `Depth: infinity` and a missing `Depth`, a header that cannot be read as the header it is (400 or, for a condition, 412), `PUT` with a declared length over `max_resource_size` or a body that is not UTF-8, `MOVE` onto itself, a sync token that is no token, a multiget with too many hrefs, a report the server does not know, `If-Schedule-Tag-Match` that is no tag | None of these depends on whether the resource exists or the caller may see it, so none tells a caller anything about a resource. |

### PROPFIND and PROPPATCH

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| `Depth` | `0` and `1`; `infinity`, and a missing `Depth` header (which means infinity in RFC 4918), are 403 `DAV:propfind-finite-depth` | PLAN 2.15. Every client sends `Depth`. |
| What `Depth: 1` lists | a home: its calendars, `inbox`, `outbox` and `notifications`; a calendar: its objects; principals, the entry point and the outbox: nothing; the inbox and the notification collection list their items (see "Collaboration over DAV"). A home is read with one call to the application (`CalendarService::list_home_collections`, which loads the authorization facts once; the dead properties and the invitations are read only when the request can ask for them), and a calendar that disappears while the listing is made, or a special collection the caller may not see, is left out of the listing instead of failing it | The members clients synchronize; R14 (no query per calendar). |
| Size of answers | an answer stops at `max_response_bytes` (32 MiB by default) with a 507 `DAV:number-of-matches-within-limits` entry for the request URI, like a truncated `sync-collection`; the resources before it are the start of the sorted list. A `calendar-multiget` that wants calendar data reads its objects in steps of 100 and stops between steps. `sync-collection` cannot be cut anywhere (its token stands for everything it reports), so its size is bounded by the number of members instead: at most `max_multiget_hrefs` per answer, and with calendar data as many as fit into `max_response_bytes` at `max_resource_size` each; the service reports the truncation with a token that continues | One request must not be able to make the server allocate gigabytes (R6, R14). The rendering is linear in what is written and bounded by the limit, so it runs inline; the XML reader, whose cost depends on the structure of the body, runs on the blocking pool with the time budget of `ical.time_budget_ms` (503 with `Retry-After` when it is spent). |
| Namespaces in answers | the four namespaces of the protocol have the fixed prefixes `D`, `C`, `CS` and `ICAL`; every other namespace a request names gets a generated prefix (`n0`, `n1`, ...) declared once on the root element, so that a request that lists a thousand properties of a long namespace does not repeat it for every resource. Names are written only if they are XML names | Answers stay small; the writer is the last line of defence against markup in a response. |
| Response order | the requested resource first, its members sorted by `href` | Multistatus output is deterministic (R9). |
| `allprop`, `propname` | `allprop` returns the live properties of RFC 4918 section 15 and the dead properties of a collection, plus those of `DAV:include`; it never carries `calendar-data`. `propname` lists the names the resource has | RFC 4918 section 9.1; RFC 4791 section 9.6 keeps the data out of `allprop`. |
| Unknown properties | a 404 `propstat` of their own; a response without any property still has an empty 200 `propstat` | RFC 4918 section 14.22. |
| `Prefer: return=minimal`, `Brief: t` | the 404 `propstat`s are left out; the answer says `Preference-Applied: return=minimal` | RFC 8144 and the older Apple form. |
| Entity tags of collections | none: the `getctag` of a calendar is its sync token, so a client that compares `getctag` and a client that runs `sync-collection` see the same change | PLAN 2.7. |
| `PROPPATCH` | atomic: when one property cannot be changed nothing is applied and the others answer 424. A property is 403 `cannot-modify-protected-property` when the server owns it (`getetag`, `sync-token`, `supported-calendar-component-set` after creation, ...), 409 when its value does not fit (`calendar-order` that is no number, `schedule-calendar-transp` without `opaque` or `transparent`), 403 when a limit is exceeded (below). A calendar the caller cannot see is 404 whatever the body says. One request changes at most 1000 properties and names at most 1000 distinct properties (400 above) | RFC 4918 section 9.2 asks for atomicity. |
| Properties clients set | `displayname`, `calendar-description`, `calendar-color`, `calendar-order`, `calendar-timezone`, `schedule-calendar-transp`; every other property is stored as XML exactly as written (dead property). Limits, all **403** (PLAN 2.15 says 403 for dead properties; the application's own `InsufficientStorage` for the 51st property of a binding is shown as 403 as well, so a client sees one status whoever finds the limit): a dead property of at most `max_dead_property_size` (4 KiB), the text of `displayname`, `calendar-description` and `calendar-color` of the same size, a `calendar-timezone` of at most `max_resource_size`, and at most `max_dead_properties` (50) dead properties set by one request or held by one binding. `MKCALENDAR` and extended `MKCOL` count and cap exactly like `PROPPATCH`. A `calendar-timezone` that is no valid iCalendar is the application's to refuse (the property is a 409 whose `propstat` carries `CALDAV:valid-calendar-data` in its `D:error`, RFC 4791 section 5.2.2: the application reports the precondition per property in `PropertyOutcome::precondition`, whatever exactly is wrong with the value) | The properties of Apple, DAVx5 and Thunderbird; PLAN 2.15. Whether a property is per binding or shared is decided by the application (PLAN 2.6). |
| `PROPPATCH` of an object, the home or the inbox | every property is 403 `cannot-modify-protected-property` (the home and the inbox are defined for the method because clients set default alarms and the default calendar for invitations there; the data model has no properties of a home, so nothing is stored, see "Collaboration over DAV") | Objects have no properties a client may change. |

### Object methods

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| `PUT` | 201 created, 204 replaced; `ETag` only when the stored bytes equal the request body; `Schedule-Tag` for scheduling objects. The body must be UTF-8 (403 `valid-calendar-data` otherwise); a body above `max_resource_size` is 403 `max-resource-size`, refused from the declared `Content-Length` before it is read | RFC 4791 sections 5.3.2 and 5.3.4. |
| Conditional writes | `If-Schedule-Tag-Match`, then `If-Match`, then `If-None-Match: *`, all evaluated by the application (PLAN 2.7). A weak tag never satisfies `If-Match`. An `If-Schedule-Tag-Match` the server never issued fails with 412, and so does any conditional header with a value that is not visible ASCII (it cannot name a tag the server issued). Every occurrence of a header counts. `If-Schedule-Tag-Match` takes one tag; a list of tags is 501 | A condition that cannot match must fail, not be ignored. |
| `If-None-Match` with entity tags on writes, the `If` header | 501 for the first; the second is not evaluated | `WritePrecondition` cannot express the first and no supported client sends either. A write that silently ignored a condition could lose data. |
| `GET`, `HEAD` | `Content-Type: text/calendar; charset=utf-8; component=vevent` (or `vtodo`, `vjournal`), `ETag`, `Schedule-Tag`, `Last-Modified`, `Cache-Control: private, no-cache`; a matching `If-None-Match` is 304, a failing `If-Match` 412 | Clients revalidate. |
| `DELETE` of an object | 204; conditional like `PUT`; `Schedule-Reply: F` suppresses the decline an attendee's deletion would send | RFC 6638 section 8.1. |
| `MOVE`, `COPY` | only between calendar object resources of this server. `Overwrite` defaults to `T`, `F` against an existing target is 412, the same source and target is 403, a `Destination` that names no object resource (a collection, the inbox) is 403, one on **another server** is 502 (RFC 4918 sections 9.8.5 and 9.9.4), one that names no resource of this server (a path outside the namespace) is 400. A `Destination` URL is ours when its scheme, host and port are those of the DAV base URL or of the `Host` of the request; `https://host` and `https://host:443` are one server. A destination in a calendar the caller cannot see, or of another tenant, is 404 and changes nothing. A copy keeps the UID, so a copy into the same calendar is 403 `no-uid-conflict`; a move within one owner is a relocation (PLAN 2.7). The conditions of a `COPY` (`If-Match`, `If-None-Match: *`, `If-Schedule-Tag-Match`) are evaluated against the source, as RFC 9110 asks, before anything is copied | RFC 4791 section 5.3.2.1, RFC 4918 sections 9.8 and 9.9. Collections are not moved or copied: calendars are made with `MKCALENDAR` and renamed with `displayname`. |

### Collections

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| `MKCALENDAR` | creates the calendar at the URL it is sent to, from the properties of its body; no body gives the defaults of the tenant (a name for an unnamed calendar is the application's choice). The URL must be a free binding slug of the caller's home: an existing calendar or the home is 405 `DAV:resource-must-be-null`, the inbox, outbox and notification collection do not define the method (405 with `Allow`) | RFC 4791 section 5.3.1. |
| Extended `MKCOL` | creates a calendar when `DAV:resourcetype` of the body names `CALDAV:calendar`; any other body, and a `MKCOL` without one, is 403 `DAV:valid-resourcetype` | RFC 5689; the server makes calendars, nothing else. |
| Bodies that create nothing | the home must be visible first (another user's or another tenant's home is 404 for every body). The properties are then read and validated before anything is created. A request that cannot create the calendar is **403** with a `CALDAV:mkcalendar-response` or `DAV:mkcol-response` that gives every property its status as RFC 4791 and RFC 5689 show: 403 with `DAV:cannot-modify-protected-property` for a protected property, 403 for a value that is too large or a dead property beyond the 50th, 409 for a value that does not fit, 403 with `DAV:valid-resourcetype` for the `resourcetype` of a `MKCOL` that does not name a calendar (also when the body does not name one at all), 424 for the properties that were fine. A body that is no creation request (malformed XML, another root element, `DAV:remove`) is 400, a body above `max_request_body` 413. A property set twice has the last value, as in a `PROPPATCH` | A refused request leaves no calendar behind; the statuses are those of `PROPPATCH`. |
| `DELETE` of a collection | 204; the application decides whether the calendar disappears for everyone or only the caller's binding (PLAN 2.9). `If-Match` is accepted as `*` only, because collections have no entity tag, `If-None-Match: *` fails (the collection exists), and a header that cannot be read fails; every occurrence counts | PLAN 2.9. |

### Reports

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| `calendar-query` | the filter becomes the filter of `davhaven-ical`; a filter the server cannot read or evaluate (two root `comp-filter`s, an unknown collation, a bad time range) is 403 `CALDAV:valid-filter`; the component of a single `comp-filter` narrows the candidates of the store | RFC 4791 section 9.7. Not evaluated: the `CALDAV:timezone` element of the query (floating times are evaluated in the time zone of the calendar), and the `Depth` header of a report (the members of the collection are always covered; clients send `Depth: 1`). `free-busy-query` is defined for calendar collections only, on a home it is 403 `DAV:supported-report` |
| `calendar-multiget` | up to `max_multiget_hrefs` (1000) hrefs, more is 403 `DAV:number-of-matches-within-limits` whether the DAV layer or the application finds it (a query or a synchronization that matches too much is 507 instead); an href that names nothing visible, another collection's object, another user's or tenant's calendar, or garbage is a 404 entry that says nothing more; two spellings of one resource (`%40` and `@`, an absolute URL, a path) are one entry, **answered with the canonical path of the resource** (an href that names nothing of the namespace is answered as the client wrote it); answers are matched to hrefs by resource, not by position; a multiget that names nothing needs a visible collection (404 otherwise) | RFC 4791 section 7.9. A multiget cannot be a way to read objects of another collection. |
| `sync-collection` | `sync-level` 1 only (`infinite` is 403 `DAV:sync-traversal-supported`: RFC 6578 gives the request no status of its own, and 403 is the one RFC 4918 section 16 uses with a precondition element); a token the server cannot use is 403 `DAV:valid-sync-token`; a deleted member is a 404 entry; a member that changed twice is reported once with its latest state; members are sorted by href. A truncated answer (`DAV:nresults`, or the server's own limit: `max_multiget_hrefs` members, fewer when the answer carries calendar data) has a 507 entry for the request URI with `DAV:number-of-matches-within-limits` and the token that continues where it stopped | RFC 6578 sections 3.3 to 3.6. Calendars, the inbox and the notification collection are synchronized this way. |
| `sync-collection` properties | a request for nothing but `getetag` is answered from the change log; any other property reads the changed members with multiget semantics, in batches of `max_multiget_hrefs` | The change log knows names and tags only. |
| `free-busy-query` | answered with a `text/calendar` `VCALENDAR` with one `VFREEBUSY` of merged periods (`FBTYPE` for tentative and unavailable time), not a multistatus, rendered by `davhaven_ical::freebusy::render_collection_freebusy` (the periods of one kind are one `FREEBUSY` property of several values, folded at 75 octets). `DTSTAMP` is the moment the application answered (its `Clock`, `FreeBusyResult::generated_at`) and the `UID` is derived from collection and range, so a repeated query names the same `VFREEBUSY` again | RFC 4791 section 7.10. The DAV layer has no clock (R9): it is handed the time instead of making one up. |
| `expand-property` | on principals, for `group-membership`, `group-member-set` and the proxy properties of CalendarServer (`calendar-proxy-read-for`, `calendar-proxy-write-for`), which are always empty. **One level of expansion**: the properties asked of the principals a property points to are answered, nested `property` elements below those are 400. A property that is listed twice is one property (nested properties merged); the names must be XML names and the namespaces at most 1 KiB (400); the principals are read once for the whole request with one call (`PrincipalService::dav_properties_many`), and a request that would expand more principals than a multiget may name (`max_multiget_hrefs`) is 403 `DAV:number-of-matches-within-limits` | Delegation is not part of 1.0. |
| Other reports | 403 `DAV:supported-report`, also for a report on a resource that does not support it: `sync-collection` of a calendar home is one of these (the home lists no report in its `supported-report-set`; clients list the home with `PROPFIND` `Depth: 1` to learn of new and removed calendars and synchronize each calendar on its own) | RFC 3253 section 3.6. |

### Errors, limits and security

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| Error bodies | the status and the precondition element of the problem catalog in a `DAV:error` document: `DAV:need-privileges` names the resource and the privilege, `CALDAV:no-uid-conflict` and `CALDAV:unique-scheduling-object-resource` the href that causes the conflict (the application names an object the caller may read; see `ObjectService::put`). Statuses without a precondition (401, 404, 501) have an empty body. The four answers the RFCs define for conditions that only the DAV layer finds are rows of the catalog too, like every other failure, and are tested in the table next to the others: `unsupported-report` (403 `DAV:supported-report`), `too-many-hrefs` (403 `DAV:number-of-matches-within-limits` for a multiget and a share request; a query or a synchronization that matches too much is `too-many-matches`, 507, with the same element), `sync-traversal-unsupported` (403 `DAV:sync-traversal-supported`) and `foreign-destination` (the 502 of a `Destination` on another server, with an empty body) | Internal error text, parser messages and identifiers of other tenants never reach a client. |
| Authentication | `Authorization: Basic` with an app password; a 401 carries `WWW-Authenticate: Basic realm="{tenant}", charset="UTF-8"`; API tokens are not accepted on DAV | PLAN 2.6. |
| XML requests | a `DOCTYPE` is refused, which rules out entity expansion; only the five predefined entities and character references are resolved; the body must be UTF-8 and well-formed; depth 32, 10 000 elements, 32 attributes per element and 64 namespaces are the limits (400); a namespace URI of more than 1 KiB and a local name of more than 256 bytes are refused (400) before they are copied, and a namespace is held once per document however often it is used; a request names at most 1000 distinct properties; control characters are refused, in text and in attribute values; an **element** in the namespace of the `xmlns` prefix, or in the XML namespace (`<xml:x/>`, which Namespaces in XML allows), is refused (400), because the answer declares the namespaces it names and neither can be declared under another prefix or as the default one, so such an element could not be written back (the attribute `xml:lang` is kept). The reader runs on the blocking pool with a wall-clock budget (`ical.time_budget_ms`, 503 with `Retry-After`) | PLAN 2.15 and R6: bodies come from the internet. |
| Body sizes | XML bodies above 256 KiB are 413; a calendar object above `max_resource_size` is 403 `CALDAV:max-resource-size`; nothing larger than the two together is read at all (the ceiling of the DAV edge is set in `router.rs`, because `davhaven_http::body_ceiling` answers the larger of the two for DAV, which would make a `PUT` just over the limit a 413 instead of that 403) | RFC 4791 asks for the precondition on `PUT`. |
| Writes from browsers | an unsafe method with an `Origin` outside `security.cors.allowed_origins` is 403; DAV has no CORS | PLAN 2.15. |
| Not supported | `LOCK`, `UNLOCK`, the `If` header, `Depth: infinity`, `sync-level` infinite, RFC 3744 ACL writes, moving or copying collections, RFC 8607 managed attachments, the per-user alarm overlay ([ADR-0004](adr/0004-shared-alarms.md)), the `CALDAV:timezone` element of `calendar-query`, the `symbolic-color` attribute of Apple's `calendar-color` (the color is kept, the name Apple shows for it is not), a list of schedule tags in `If-Schedule-Tag-Match`, `sync-collection` of a calendar home | Non-goals and backlog entries of PLAN 1 and `docs/ROADMAP.md`. |

## Collections, bindings and sharing (CalendarServer extensions, PLAN 2.9)

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| Where a calendar appears | every visible calendar is a *binding* in the viewer's home: the owner's at creation, a sharee's when the invitation is accepted, and those of group calendars, managed calendars and API grants on the first listing of the home | Clients know collections by their name in the home; the same calendar can have another name for everybody who sees it. |
| Names of bindings | the calendar's slug unless the home uses it already, then `-2`, `-3`, ... The slug of a calendar never changes; display names do | Two calendars called `shared` (an own one and a group's) must both be addressable. |
| Properties of a collection | `displayname`, `calendar-color`, `calendar-order`, `schedule-calendar-transp` and every dead property belong to the viewer's binding and are always writable by it; `calendar-description` and `calendar-timezone` belong to the calendar and need write access (403 for a read-only sharee). Dead properties: at most 50 per binding, 4 KiB each (507) | PLAN 2.6: a read-only sharee may colour a calendar for themselves, never describe it for the owner. |
| `PROPPATCH` | all or nothing: when one property is refused, none is applied and the others answer `424` | RFC 4918 section 9.2. |
| `MKCALENDAR` and extended `MKCOL` | create a user calendar in the caller's own home; a taken name is `resource-must-be-null`; components default to what the tenant allows, others are `supported-calendar-component`; an unusable `calendar-timezone` is `valid-calendar-data` | RFC 4791 section 5.2.2. |
| `DELETE` of a collection | the owner deletes the calendar for everybody (soft delete, purged after `retention.deleted_calendar_days`); a sharee leaves the share (the grant is declined, the owner is told by a notification); a member of a group or a grantee of a managed calendar hides the binding for themselves, and a hidden binding is not recreated by the next listing. **A calendar that a grant marks `required` is not deleted by its people at all**: the answer is `403` with `DAV:need-privileges` naming `DAV:unbind` on the home, the parent of the collection (RFC 4918 section 9.6.1), and nothing changes | PLAN 2.9. No operation of the management API removes a binding, so there is no API side of this refusal. A calendar app has no way to bring a hidden binding back, so what the operator needs everybody to have (the calendar of a team, the catalogue of courses) must not be one DELETE away from disappearing. The operator marks it with `required` on the grant (`PUT …/grants/{grantee}`); an optional calendar keeps the hiding, and `GET …/principals/{principal}/bindings` and `POST …/bindings/{binding}/restore` list and show again what somebody hid. |
| `required` grants | `required: true` on a grant of the management API makes the calendar mandatory for everybody the grant reaches: the grantee, or the members of a grantee group, for as long as the grant is accepted (API grants always are). Bindings that were hidden before the flag come back with it, and so do those of people who join the group later (the membership change brings them back, in its transaction, and audits each as `binding.restored`). The flag belongs to the grant, so a `PUT` without it makes the grant optional again: a client that reconciles grants sends `required` on every `PUT`. Only a tenant token sets or clears it and removes a grant that has it (`403` for a principal's token, which keeps the flag a grant has when it puts one). Client sharing never sets it, and a client cannot change or remove a grant that has it (`403 DAV:need-privileges`), even on a user's own calendar. A group that owns its calendar may be granted that calendar, which is how the calendar is marked required for its members | A grant to the owner is refused for users (the owner has access already) but a group's members get the group's default access without a grant, so the grant of the group to its own calendar carries nothing but the flag: its access is `read`, the floor of the grants, which never raises what the members have (`422` for another level), and removing it keeps the group's own binding. |
| Sharing flow | `CS:share` creates a *pending* grant and a `CS:invite-notification` in the sharee's notification collection; the sharee answers with `CS:invite-reply` (`CS:shared-as` names the new binding); the owner gets an `invite-reply` notification. `sharing.auto_accept` skips the notification and the binding exists at once. Answering twice with the same answer repeats the first; declining ends the share and takes the collection out of the sharee's home. Summaries and display names are cut to 200 characters, the owner's and the sharee's alike | What Apple Calendar does. |
| Who may be shared with | active users and groups of the same tenant; each item of a request has its own answer, so one external address (`403` with `invalid-sharee`) does not stop the others. A group needs no answer: its current members have the access through the group | PLAN 2.9. |
| Who may share | the owner and administrators; never managed or mirror calendars through DAV, and not at all where the tenant or the deployment turned sharing off (DAV: `403` with `sharing-not-allowed`, to a caller who can see the calendar; to everybody else the answer is the usual 404, whether sharing is on or off). The management API follows the same switches for the tokens of principals (`409 feature-not-enabled`); a tenant token administers access whatever they say | PLAN 2.9. |
| API grants and DAV shares | one grant per (calendar, grantee): the last write wins, `source` says who wrote it. The API grants to users, groups and **service principals** (the machine identities that hold principal tokens for the API and MCP: an assistant is given the calendars it may use this way); client sharing stays with users and groups, and a service principal is not found by principal search. A grant made through the API is effective at once and withdraws a pending invitation; clients can neither remove nor rewrite the API's grants on group and managed calendars (`CS:share` `set` and `remove` answer `DAV:need-privileges` for that item; a `set` would turn the grant into a client's own). A service principal is no sharee of client sharing, on any kind of calendar: it is not listed in `CS:invite`, a `set` for it answers `DAV:invalid-sharee` and a `remove` `DAV:need-privileges`, so a client never lists or undoes the grant of an integration | The integration that provisions access must not be undone by a client. |
| Deleting a principal | its credentials, RSVP links, shares in both directions and memberships end at once; the principal is hidden, its name, its external reference and its addresses stay reserved until the purge (mail to a reserved address is not treated as external). `PUT` with `If-None-Match: *` for the name of a deleted principal answers `412`, exactly as for a name that exists and without a hint about the hidden principal, and without the header `409 name-reserved`; a create or replace whose `external_ref` or address collides with it answers `409 external-ref-reserved` or `409 address-reserved` (a collision with a live principal is the plain `409 conflict`), so a provisioning client can purge the hidden principal or wait for the retention period. Every grant that ends is audited (`share.removed`) and announced (`grant.deleted`), every membership too (`membership.changed`), and the CTag of each calendar that lost a grant moves. Deleting a group ends the access of its members in the same transaction: their bindings of the group's calendars and their memberships go with it | PLAN 2.10. |
| Notifications | the collection of a principal holds invitations and replies; clients delete them after showing them, and answering an invitation does not need the notification to be there | A client that cleaned up must still be able to answer. |

## Collaboration over DAV (CalendarServer sharing, RFC 6638 collections, principal search)

What the modules `sharing`, `notifications`, `scheduling` and `principals_search` of `davhaven-dav` do. What the
application decides (who may share, who may be invited, what a reply changes) is in the sections above and below;
these rows are about what a client sends and reads. The request bodies of Apple Calendar and of other clients are
kept byte for byte in `testdata/dav/sharing` (see its `README.md`).

### `POST`

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| Where `POST` is defined | on a calendar collection (`CS:share`), on a calendar home (`CS:invite-reply`) and on the outbox (a `VFREEBUSY` request); every other resource answers 405 with `Allow` | The three requests of the CalendarServer and RFC 6638 flows. A sharee's reply goes to the home, as Apple Calendar sends it. |
| Media type | the body of a sharing request must be XML (`application/xml`, `text/xml` or any `+xml` type such as `application/davsharing+xml`), the body of an outbox request `text/calendar`; anything else, a missing `Content-Type` included, is 415 with an empty body, **before** the resource is looked at | PLAN 2.15: a web page can send a `POST` with the credentials the browser remembers, but only as `text/plain`, `multipart/form-data` or a URL-encoded form without asking the server first. A request that has to name an XML or calendar media type cannot be forged by a form. The refusal looks at the request alone, so it is the same for every resource. |
| What is read first | the media type, then the body (XML limits of PLAN 2.15: 256 KiB, depth, elements, namespaces, no `DOCTYPE`; an outbox message at most `max_resource_size`), then the application. A body that cannot be read or does not make sense, and a request that names too many sharees, is 400 (403 for too many) for a caller who can see the resource and **404 for one who cannot**: the refusal is judged only after the services said the resource is visible. The outbox is resolved **before** its body is read, whatever the body is: the application is handed the name of the owner, which says nothing about the tenant of the path or who may use the outbox, so only resolving the outbox (404 for another tenant's, another principal's and an unknown outbox) decides that | A refusal must never tell a stranger that a calendar, a home or an outbox exists (PLAN 2.6), and a request must never reach the outbox of somebody else under the name of its owner. |
| Media types the server does not read | no `multipart`, no JSON, no form encoding; `CS:share` documents may arrive with `Content-Type: text/xml` (older clients) | Only XML and iCalendar are defined for these requests. |

### Sharing requests

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| `CS:share` | `CS:set` (a sharee, optionally `CS:common-name` and `CS:summary`, and exactly one of `CS:read` and `CS:read-write`) and `CS:remove` (a sharee) in any number; elements of other names are ignored. The sharee is named by the `D:href` of a calendar user address: `mailto:`, `urn:uuid:`, a principal URL or an `http(s)` URL; the application resolves it within the tenant. A body without a single `set` or `remove`, an item without a valid address, a `set` without or with two access levels is 400, and so is a body that **names the same address twice** (however it is spelled, in any combination of `set` and `remove`): the application applies every `set` before every `remove`, so a body that removes a sharee and invites them again would end with the sharee removed, and a `multistatus` answers every resource once | What Apple Calendar sends (`share-set-read-write.xml`, `share-set-read.xml`, `share-remove.xml`, `share-set-and-remove.xml`). A request that depends on an order it cannot express is refused instead of guessed. |
| Number of sharees | `set` and `remove` count together, at most `limits.dav.max_sharees_per_request` (100 by default, configurable) per request; more is 403 `DAV:number-of-matches-within-limits`, before the application is asked and only for a caller who can see the calendar (404 for others). The limit is its own and not the one of a multiget: every sharee is a lookup of the application and a notification in the sharee's collection, so raising the number of hrefs a multiget may name does not raise it | A request must not be able to ask for a million, nor to put a thousand notifications into other people's collections. |
| The answer | 200 without a body when every item was applied. When some were refused the answer is a **207** with **one `response` for every item**, as CalendarServer answers: 200 for an item that was applied, and for one that was not the status and the precondition of its problem (403 for an address outside the tenant, 403 `DAV:need-privileges` for a grant the API made on a group or managed calendar). The responses are **sorted by `href`** and the `href` is the **text the client sent** (`mailto:Ben.example` is answered as sent, not as the lower-case address the application works with); every sharee is named once (a body that names one twice is 400), so no `href` is answered twice. The applied items **were applied** | Items are independent (PLAN 2.9), so one external address does not stop the others; a client that gets a 207 matches the responses to its items by `href` and reads which sharee to correct. |
| `CS:invite-reply` | exactly one of `CS:invite-accepted` and `CS:invite-declined`, the invitation it answers in `CS:in-reply-to` (a valid invitation id of at most 255 characters), optionally `CS:summary`. `CS:hosturl` is read when it names a resource of this server (a path-absolute reference, or an absolute URL on the origin of the public or the DAV base URL) and ignored otherwise: an absolute URL of another host is no resource of this server, whatever its path says; `CS:common-name` is ignored. Accepting answers 200 with a `CS:shared-as` document naming the collection in the sharee's home (`invite-reply-response.xml`), declining answers 200 without a body. Answering the same invitation twice with the same answer repeats the first | The invitation identifies the share; the URL and the names are the client's notes of where it came from. |
| Who may reply | the owner of the home; a reply to somebody else's home is the application's 404 or 403 | PLAN 2.9. |

### Notifications

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| The collection | `notifications/` of the home: `PROPFIND` (`Depth: 1` lists the notifications sorted by `href`) and `REPORT sync-collection`; no `POST`, no `MKCOL`. `calendar-multiget` and `calendar-query` are 403 `DAV:supported-report` | The reports Apple Calendar sends (`propfind-notifications.xml`, `sync-notifications.xml`). |
| A notification | `GET` and `HEAD` answer the XML the application stored (`text/xml; charset=utf-8`) with `ETag` and `Last-Modified`; a matching `If-None-Match` is 304 and a failing `If-Match` 412. `DELETE` answers 204 and is conditional like every write (below); deleting does not withdraw the invitation. The properties are `getetag`, `getcontenttype`, `getcontentlength` (the size the application reports), `getlastmodified`, `creationdate`, `CS:notificationtype` (`<CS:invite-notification shared-type="calendar"/>` or `<CS:invite-reply shared-type="calendar"/>`) and the privileges the application reports for it (`read` and `read-current-user-privilege-set`; the DAV layer renders them and decides nothing). `Last-Modified` and `getlastmodified` are the date the notification was **last written** (it is rewritten in place when the sharee's access changes), `creationdate` the date it was created | Clients list the collection, read each notification, show it and delete it. The date goes with the entity tag: a client that compares dates sees a rewritten invitation. |
| Conditional `DELETE` | the conditions of the request (`If-Match`, `If-None-Match: *`) go to the application (`SharingService::delete_notification_if`), which evaluates them against the stored entity tag **in the transaction that deletes**, as `ObjectService::delete` does: a client that read an invitation and deletes it with `If-Match` cannot remove a newer version that the application wrote in place in between (412, nothing deleted). A notification has no schedule tag, so `If-Schedule-Tag-Match` never holds. A plain `DELETE` costs one call. **Inbox items** are different: the store never rewrites an item (it has no update, only creation and deletion), so its entity tag cannot change between the comparison and the deletion and the conditions are evaluated by the DAV layer against the item as it is read just before | The race is real for notifications and does not exist for inbox items. |
| Bodies | produced once by the application when the notification is created (`notification-invite.xml`, `notification-invite-reply.xml`) and served as stored | The ETag of a notification is the hash of its bytes, so the DAV layer must not rewrite them. |

### Scheduling inbox and outbox (RFC 6638)

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| Outbox | `POST` of `text/calendar` with a `METHOD:REQUEST` `VFREEBUSY`. The originator is the `ORGANIZER` of the message, which has to be an address of the outbox owner (the application checks it against the addresses of the principal), and the recipients are its `ATTENDEE`s (RFC 6638 section 5); RFC 6638 defines no `Originator` and `Recipient` request headers (they belong to the drafts that preceded it), so none is read. Other kinds of message are refused by the application (400 `CALDAV:valid-scheduling-message`; so is a body that is not UTF-8). A message above `max_resource_size` is 403 `CALDAV:max-resource-size` | RFC 6638 takes originator and recipients from the message; PLAN 2.8 admits `VFREEBUSY` only. |
| The answer | a `CALDAV:schedule-response` with one `response` per recipient in request order: `Delivered` is `2.0;Success` with the reply `VFREEBUSY` as `calendar-data`, `Queued` is `1.0;Pending`, `ImipSent` `1.1;Sent`, an address the server cannot resolve `3.7;Invalid Calendar User`, a failed delivery `5.1;Service unavailable` | RFC 6638 section 10.1 and RFC 5546 request statuses. |
| Inbox | `PROPFIND` (`Depth: 1` lists the items sorted by `href`), `REPORT sync-collection` and `calendar-multiget`. `calendar-query` is **not supported** (403 `DAV:supported-report`, a backlog item in `ROADMAP.md`): clients that poll the inbox use the other two. Quarantined messages are never listed | Apple Calendar and Thunderbird synchronize the inbox like a calendar. |
| Reading the messages | the listing of the application carries everything a request can ask for except the messages (entity tag, **size**, dates, privileges), so only a request for `calendar-data` reads them: in **steps**, one call of the service for each (`SchedulingService::inbox_get_many`, R14: never one call per item), a step holding as many messages of `max_resource_size` as `max_response_bytes` takes (at most 100 and `max_multiget_hrefs`). `getcontentlength`, `allprop` and `propname` read none (`propname` names `calendar-data` without rendering it). The `calendar-data` selection of the request (components, properties, expansion, limit-recurrence-set) goes to the service with the paths, which cuts the message down to it as it does for calendar objects. **The bulk read is the service's**: the application implements it in one transaction (one query for all the items, the home resolved once with the tenant of the path), and a service that does not answers 501 to the requests that need it | Bounded memory (PLAN 2.15, R6): one request must not make the server allocate gigabytes; and no read of a message for what the listing already knows. |
| Inbox `PROPFIND` that is too large | the messages are read in the order of the hrefs and reading stops when what has been read exceeds `max_response_bytes`: the answer is the **sorted prefix** and a 507 `DAV:number-of-matches-within-limits` entry for the request URI, like every other answer that grows too large (the client then synchronizes with `sync-collection` and `calendar-multiget`) | One protocol, one truncation rule. |
| Inbox `sync-collection` | the entity tags alone are answered from the change log. A request that asks for more reads the **changed members by path** with the bulk read (without their messages unless `calendar-data` is asked for), never the whole inbox, and reads nothing when nothing changed. A request that needs the messages (`calendar-data`) asks the application for as many changes as fit `max_response_bytes` (the rest is a 507 entry for the request URI and the token that continues). The application lists **every** member of an initial synchronization (no token) without cutting it, so an initial synchronization that asks for the messages is refused with 507 when they would exceed `max_response_bytes`, after reading no more than that and a step: the client asks for the entity tags (and sizes) first and fetches the messages with `calendar-multiget`. One that asks for the sizes is not refused for them | An answer of a synchronization cannot be cut anywhere: its token stands for everything it reports. |
| An inbox item | `GET`, `HEAD` (`text/calendar; charset=utf-8`, `ETag`, `Last-Modified`) and `DELETE` (204, conditional as described under *Conditional `DELETE`* above); `PUT` and `MOVE` are 405: the server delivers items, clients only remove them. The properties are `getetag`, `getcontenttype`, `getcontentlength`, `getlastmodified`, `creationdate`, `calendar-data` and the privileges the application reports (`read` and `read-current-user-privilege-set`) | RFC 6638 section 3.2.2. |
| `calendar-multiget` of the inbox | the named items, read in steps like a listing (one call per step with the `calendar-data` selection of the request, a 404 entry for what the application does not find); an `href` that names another inbox's item, a calendar object or no resource of the namespace is a 404 entry that says nothing more. The inbox must be visible (404 otherwise, before the body is judged), at most `max_multiget_hrefs` hrefs (403); the answer is cut at `max_response_bytes` with a 507 entry for the request URI | A multiget cannot be a way to read the inbox of somebody else. |
| `Schedule-Tag` | the application's tag, passed on unchanged: as the header of `GET`, `HEAD` and `PUT`, as the property `CALDAV:schedule-tag`, and back as `If-Schedule-Tag-Match` on writes. It changes when the organizer changes the event and when an attendee changes their own copy, and **not** when the server merges a reply or a `SCHEDULE-STATUS` into the organizer's copy (PLAN 2.7), so a client that holds the tag can write on top of the merges instead of getting a 412 | RFC 6638 sections 3.2.10 and 3.2.11. |
| `schedule-default-calendar-URL`, default alarms of the home | not stored: a `PROPPATCH` of the home or the inbox is 403 `cannot-modify-protected-property` for every property. Invitations are added to the calendars by the scheduling policy of the application (PLAN 2.8), not to a calendar the client picks | The data model has no properties of a home (PLAN 2.4); the property is a backlog item in `ROADMAP.md`. Clients keep working when the `PROPPATCH` is refused. |

### Principal search

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| Where | `REPORT` to the entry point `/dav/` (the `principal-collection-set` of every resource) or to a principal URL that the caller can see; both advertise the three reports in their `supported-report-set`. Every other resource is 403 `DAV:supported-report`, a principal of another tenant 404. **Deviations from RFC 3744 sections 9.4 and 9.5**: a search sent to a principal covers the whole tenant like one sent to the entry point, whether or not it says `DAV:apply-to-principal-collection-set` (the RFC limits it to the principals under the request URI without it); and the `Depth` header is not evaluated, every value is answered as `0` (the RFC makes the reports `Depth: 0` and answers other values with 400) | Apple Calendar sends its search to the principal collection; clients differ in where they send it and which `Depth` they say, and what a search finds does not depend on either, so refusing them would only break clients. |
| `CS:calendarserver-principal-search` | `CS:search-token` (at most `limits.dav.max_search_terms`, 8 by default; **every** token must match the name, the display name or a stored address, however short a token is: a client that splits "Anna B" sends `anna` and `b`, and "Anna B" finds Anna Bauer in a tenant with sixty people called Anna), `context` (`attendee`, the default: people, groups and resources; `user`; `group`; `location` and `resource`: resources), `type` (a calendar user type that narrows it further; an unknown one does not narrow) and `CS:limit/CS:nresults` (at most 50, at least 1). An unknown `context` finds nothing. **One search**: all the tokens and the kinds of `context` and `type` are conditions of the one search the application makes, applied before the limit of 50, so a person is found whatever else matches the first token. No token of two characters, no kind of principal, or a token longer than 512 characters (no address is longer): nothing is found and the application is not asked | `calendarserver-principal-search.txt` of CalendarServer; Apple Calendar looks up attendees while the user types. |
| `DAV:principal-property-search` | up to `limits.dav.max_search_terms` `property-search` elements with `D:prop` and `D:match` (`match-type` `contains`, the default, `starts-with` or `equals`, ignoring case), combined with `test` `allof` (default) or `anyof`. Searchable are `displayname`, `calendar-user-address-set` and `CS:email-address-set` (the e-mail addresses without their scheme); a `property-search` that names none of them is never satisfied. The search is **one search** of the application with every `property-search` as a criterion (the properties it names, its text, its match type) and `allof` or `anyof` as it says, all applied before the limit: with `allof` one text of two characters is enough to ask, the others may be shorter (`displayname` contains `Anna` and an address starts with `a`); with `anyof` a `property-search` that names no searchable property or has a text shorter than two characters adds nothing to the union. A text of more than 512 characters finds nothing. Only what the application stores is searched: the principal URL and the `urn:uuid:` address that `calendar-user-address-set` shows are derived and not found by any search | RFC 3744 section 9.4, with the properties `principal-search-property-set` lists. |
| `DAV:principal-search-property-set` | the three searchable properties with an English description | RFC 3744 section 9.5. |
| Bounds | the same tenant as the caller and no other; a search that has **no text of two characters finds nothing** (an empty `multistatus`, not an error, so a client that searches while the user types has nothing to handle), and so does a text of more than 512 characters, which is no address, name or part of one; at most **50** principals, ordered by `href`; only active principals; service principals are never found; a search without a text is 400. The application matches a text against names, display names and the stored addresses **with their scheme** (`mailto:...`), so a two-character text such as `ma` or `to` also matches every principal that has an e-mail address: the minimum of two characters narrows what a text can be, it does not make a search of the whole tenant impossible | PLAN 2.9: the search must not be a way to read other tenants, and it bounds what one request returns. |
| A cut answer | when the limit (50, or `CS:nresults`) cut the answer, the `multistatus` ends with a 507 `DAV:number-of-matches-within-limits` entry for the request URI, as CalendarServer answers, so a client knows that there are more people than it was shown and can refine the search. The application asks its store for one more than the limit to know. The principals in the answer are the first by display name, sorted by `href` in the document | Without it a cut answer looks complete. |
| Configuration | `limits.dav.max_search_terms` (8) and `limits.dav.max_sharees_per_request` (100) are in the `[limits]` table; the longest text of a search is the longest calendar user address (512), which is a property of the address and not a setting | R3: limits come from configuration. |
| What a hit discloses | `displayname`, `calendar-user-address-set`, `CS:email-address-set`, `calendar-user-type`, `principal-URL` and `resourcetype`. The URLs of the home, inbox, outbox and notification collection, group membership and every other property (`supported-report-set`, `supportedlock`, `current-user-principal`, ... included) are 404 `propstat`s | PLAN 2.9: display name and addresses only. |

## Writes, ETags and synchronization (PLAN 2.7)

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| `ETag` | strong, the first 22 characters of the base64url encoding of the SHA-256 of the stored bytes in quotes, the same in `GET`, `PROPFIND`, `REPORT` and the API | One value a client can compare wherever it sees the object. |
| `ETag` of a `PUT` response | present only when the stored bytes are the request body; when the server rewrote them (scheduling writes `SCHEDULE-STATUS`) there is none and the client reads the object again. What the scheduler returns is prepared again before it is stored, so the index, the content hash and the attendee rows describe the stored bytes | RFC 4791 section 5.3.4. |
| Alarm state from read-only bindings | a `PUT` of an object by a caller who may only read it, whose bytes differ from the stored ones in nothing but the acknowledgement and snooze state of alarms (`ACKNOWLEDGED`, `X-MOZ-LASTACK`, `X-MOZ-SNOOZE-TIME*`), is answered `204` without an `ETag` and stores nothing; anything else from a reader is `403` | ADR 0004 rule 2: Thunderbird and Apple write these back from shared calendars, and an error would show as a sync failure. |
| Conditional headers | evaluated in the order `If-Schedule-Tag-Match`, `If-Match`, `If-None-Match: *` under the lock of the calendar; a current `Schedule-Tag` excuses a stale `ETag` only where the scheduler merges the attendee's change | PLAN 2.7. |
| Sync token and `CTag` | one string, `urn:davhaven:sync:{collection}:{epoch}:{seq}`; every change of the calendar (object, property, share, binding) moves it exactly once. The inbox and notification collections have tokens of their own. A home has none over DAV (neither `DAV:sync-token` nor `CS:getctag`, and `sync-collection` of it is 403); the application service knows a token for it that no protocol reaches (see the backlog of `docs/ROADMAP.md`) | A client that sees an unchanged `CTag` skips the sync. |
| `sync-collection` | `sync-level` 1; deleted members are `404` entries; a foreign, garbled, wrong-epoch, future or pruned token is `403 DAV:valid-sync-token` (the API answers 410). A cut answer (`limit`) carries the token of its last entry; the initial answer of a calendar whose log was never pruned is cut the same way; a collection with more than `dav.max_sync_members` (100 000) members is answered with the precondition that asks for a new initial sync. The DAV layer does not serve the home: `sync-collection` of a home is 403 `DAV:supported-report` (see Reports) | RFC 6578. Calendars, the inbox and the notification collection are the collections clients synchronize. |
| Moves and copies | a `MOVE` is a relocation (same object, `ETag` and `Schedule-Tag`, a change in both calendars); between calendars of different owners a scheduling object is refused. A `COPY` keeps the UID, so a copy inside one calendar is `no-uid-conflict` | RFC 4791 section 5.3.2.2. |
| Conflicts name the resource | `no-uid-conflict` and `unique-scheduling-object-resource` carry the href of the object in the way, through the caller's own binding of its calendar when there is one. A scheduling object in another calendar of the owner is named only to a caller who can read that calendar through a binding of their own; otherwise DAV answers with the href of the caller's home and the management API with a plain `409` | RFC 4791 and RFC 6638 ask for it; nothing of what a caller cannot see may leak through the error. |
| Lost races | a transaction that loses a race (serialization failure) is repeated up to three times, then answered `503`; a lock timeout is answered `503` at once, because repeating it only keeps the connection longer | PLAN 2.7. |
| Queries | the store narrows candidates by its index (a superset), the application judges them exactly; at most `dav.max_query_candidates` (10 000) candidates, `dav.max_query_results` (10 000) results and `dav.max_query_bytes` (64 MiB) of data per query, more is `number-of-matches-within-limits`; a `multiget` takes 1000 hrefs and answers `403` with the same precondition beyond them, instead of cutting the list. The expansion of recurrences runs on a blocking thread with a time and memory budget, in chunks | PLAN 2.15. |
| Authorization | one load of the authorization facts per calendar a request is about and per deciding transaction (a JSON write decides before it reads and again under the lock, a batch twice whatever its size); a listing, a home sync and a search load those of all their calendars in one call | PLAN 2.6, checked in `crates/it/tests/appcore/facts.rs`. |
| Order of the checks | whoever may not do something is told so (`404` when the resource is invisible to them, `403` when it is visible) before the conditions (`If-Match`, create-only), the kind of the calendar, the recurrence id or the validity of the body is looked at: the answer must not depend on anything the caller may not know | PLAN 2.6, checked by the denial matrix in `crates/it/tests/appcore/events.rs`. |

## Management API and MCP semantics (PLAN 2.10, 2.12)

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| `PUT` | creates or replaces; the same body twice changes nothing: no new version, no event, no audit record. What a replace leaves out is cleared, with two exceptions: the settings of a tenant and the `status` of tenants and principals stay as they are, so a reconciler that never mentions a suspension does not undo it | Declarative provisioning must be safe to repeat. |
| `PATCH` | a JSON merge patch computed against the stored state; a concurrent change makes the request start again, unless the client named a version (`If-Match`), then it is `412` | A patch without a version is the client's wish to change those members whatever else changed. |
| `DELETE` | needs `If-Match` for tenants, principals and calendars (428 without) | PLAN 2.10. |
| Events by key | an event addressed by `external_key` that does not exist is created with the UID `UUIDv5(calendar id, key)`; a write that leaves the content hash unchanged writes nothing (same `ETag`, same sync token); JSON fields are merged into the stored component, so unknown properties, alarms and `X-` properties survive. A change or deletion of `this` instance or of `this_and_future` needs the `recurrence_id` of the instance (`422`, `/recurrence_id` required): without it the request would reach the whole series | Polling integrations must stay quiet, and clients' data must stay whole. |
| JSON event fields: value, absent, `null` | a JSON event write is a JSON Merge Patch (RFC 7396) of the fields of the event: a field with a value replaces the stored one, an absent field keeps it, a field that is `null` removes it from the stored component (`"location": null` clears the location). That holds for `summary`, `description`, `location`, `end`, `duration`, `status`, `transparency`, `class`, `recurrence`, `organizer`, `attendees`, `categories`, `url` and `alarms`, which is every field of the event model that can be empty; an empty text removes a text field and an empty list an attendee, category or alarm list. `uid` and `start` cannot be removed, and the schema does not make them nullable: `null` for one of them is `422 validation-failed` at the pointer of the member (`/start`, `/items/3/event/start` in a batch) with the code `not-nullable`, and nothing is written; `null` for `recurrence_id` and `sequence` is the same as leaving them out (they are no fields a write removes). The rule is RFC 7396 for the members of the event and no deeper: an object or a list that is sent (`recurrence`, `organizer`, `start`, `end`, `alarms`, `categories`) replaces the stored one as a whole, so `{"recurrence": {"exdates": [...]}}` drops the stored rule, and attendees are matched by address, an attendee keeping the parameters (also a `null` one) that the write does not state. `"organizer": null` is refused (`422`) while the event has attendees, and in a series with overrides the organizer of the master cannot be removed alone (`same-organizer-in-all-components`). The same rules hold for `PUT …/objects/by-key/{key}`, the `event` of a batch item and the `event` and `changes` of the MCP tools `create_event` and `update_event`. A write whose result has the content hash of the stored event changes nothing (no `ETag`, no sequence bump, no event), so a client that sends every member on every run, with `null` for the empty ones (not for `uid` and `start`), finds a settled calendar quiet. `"end": null` removes `DTEND` (`DUE` of a to-do) and the start that moves in the same write does not take the old end along; `"duration": null` removes `DURATION` | The consumer that reconciles a managed calendar must be able to repair drift and to clear a location again. A field cannot be both given and removed: that is refused (`422`) for the one who builds a request in code, JSON cannot say both. |
| `notify_attendees` | API and MCP writes schedule only when the caller asks; batches never schedule | PLAN 2.8. |
| Batch | up to 1000 entries in one transaction, all or nothing: with any failing entry nothing is written and the result lists every entry (`failed` with its problem, the others with what they would have done, without `ETag`s; the API answers 422). `replace` deletes what is missing within `replace_scope_prefix` only; `max_deletes` and `allow_empty` guard against wiping a calendar. A changed object gets a higher `SEQUENCE` than the stored one. The entries are read without the lock, merged, validated and serialized on blocking threads, and written under the lock after the bases are checked again; after the first entry that fails in the store the rest is validated but not stored. A `replace` that would delete everything in its scope without any item is `422` (`/allow_empty`) unless `allow_empty` is set; `max_deletes` is counted while the deletions are collected | PLAN 2.10. |
| Search | a search that can be examined within `limits.api.max_scanned_objects` objects is answered in start order with keyset cursors (`c1.`); a larger one is answered in scan order with a cursor that names the position (`s1.`), so a page may be empty and still carry a cursor: a client follows cursors until there is none. Every match is delivered exactly once, the instances of a recurring event included (a page may end inside a series) | PLAN 2.12. |
| Idempotency | a key is scoped to (tenant, token, key) and lasts 24 hours; the same request replays the stored response, another request with the key is `422 idempotency-key-reuse`, one still running is `409 idempotency-in-progress`; a request that never finished releases the key after its lease, which is the request timeout of the server (`server.http.request_timeout`) plus 30 seconds, whatever the timeout is set to (there is no setting for it). The request settles its key fenced by that lease (`reserve` and `settle`, ADR 0012): a request that outlived its lease neither overwrites the response of the retry that took the key over nor releases its claim. What identifies "the same request" is the fingerprint the caller passes, which must cover the concrete path: one key and body sent to two resources are two requests. Responses with secrets are not stored (`409 secret-not-replayable`) | PLAN 2.10. |
| Paging | `?limit` (default 50, at most 200) and a cursor that is signed with the key ring and bound to its listing and tenant: a cursor of another list, another calendar or another tenant is refused | The position is the id of the last item, so concurrent inserts neither repeat nor skip. |
| Tokens | a token mints tokens whose scopes are a subset of its own, and a minted token never outlives the one that minted it, with **one exception**: the `mcp:*` scopes, which a tenant token cannot hold itself. A tenant token with `credentials:write` may put them on a **principal token for a service principal**, **provided it holds the API scope that reaches the same data** (`events:read` for `mcp:read`, `events:write` for `mcp:write` and `mcp:schedule_external`: MCP, unlike DAV, does not cap managed calendars at read, so `mcp:write` reaches what `events:write` reaches there, and `mcp:schedule_external` sends invitations by mail, which the minter could not do itself without the scope); every other scope still follows the subset rule. Without the exception no token could mint the token that an assistant needs. MCP scopes need a tenant that switched MCP on and an expiry within `security.max_mcp_token_days` (90); origins are normalized to scheme, host and port | PLAN 2.6. |
| Impersonation | **`credentials:write` is the power to act as any principal of the tenant that can act** (a user, a service principal or a resource; not a group): it mints app passwords, which log in over DAV, and principal tokens, which act on the API and MCP, and what a principal token does it does *as the principal*: it sees the calendars the principal owns or is granted, writes where the principal may write, and an event it creates is the principal's (the organizer, when it invites, is the principal's address). There is no on-behalf-of and no per-request impersonation (ROADMAP). The exception for service principals (the `mcp:*` scopes only, and only with the API scope of the same reach) therefore adds the reach of MCP to what `credentials:write` already is: acting as the principal. For a **user** the plain rule stays: a token with `events:read` cannot mint a token with `events:write` for a user, and MCP scopes reach a user only from the operator (`davhaven admin principal-token create`: the command line is the operator, not a token). Every minting is audited (`token.created`: the token, its principal, its scopes and expiry, and who minted it: the minting token, or the system actor for the command line); hand `credentials:write` to provisioning, never to an integration that only needs calendars | PLAN 2.6. |
| Provisioning audit | `tenant.created` and `tenant.settings_changed` (it names every changed field, `status` and `display_name` included, never the values) are written **in the system transaction of the change**, so a tenant change that commits always has its record and one that rolls back leaves none; the schema admits exactly these two actions from system scope ([ADR-0005](adr/0005-database-role-model-and-system-scope.md)). `tenant.deleted` is logged with its actor, since the audit log goes with the tenant | A tenant is created and changed across tenants, so it has no transaction of its own to carry the record. |
| MCP writes | every write is audited (`mcp.write`, the tool and the ids, never the content) in the transaction of the write | PLAN 2.12. |

## MCP server (PLAN 2.12)

`crates/mcp` serves the Model Context Protocol for AI assistants. It calls the services of the application as the
person a token belongs to, so what an assistant may do is exactly what the same person may do over DAV and the
management API, and what it may read is what the application decides it may read: the protocol crate maps fields and
decides nothing (PLAN 2.6).

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| Transport | stateless streamable HTTP at `/mcp` (route group `mcp`, normally the `internal` listener). `POST` carries one JSON-RPC message and is answered with `application/json`; `GET` and `DELETE` are `405` with `Allow: POST`. There are no sessions: `Mcp-Session-Id` is neither issued nor read, and it is never a credential. The `Accept` header must list `application/json` and `text/event-stream`, and the body is limited to `limits.api.max_json_body` (1 MiB, `413`; a body that cannot be read at all is `400`) | Nothing is kept between requests, so any instance behind any balancer can answer, and there is no session to hijack. |
| Faults of a body | text that is not JSON is `400` with the JSON-RPC error `-32700`; JSON that is no request, notification or response, and every batch, is `400` with `-32600` (MCP has no batches since `2025-06-18`). The id of the bad request is echoed when it has one | A JSON-RPC client can act on a JSON-RPC error; the transport library answers `415` with a plain text. |
| Protocol revision | `2025-06-18`, and only that: `initialize` is answered with it whatever revision the client asks for (`2024-11-05`, `2025-03-26`, `2025-11-25`, `2026-07-28`, ...), and the client decides whether to go on. The per-request lifecycle of `2026-07-28` is refused with an unsupported-version error that lists what is supported. The server offers tools only (`capabilities.tools`, no `listChanged`: the catalog does not change while the server runs) | The plan fixes the revision (ADR-0001). `2024-11-05` is the HTTP+SSE transport, which this endpoint does not serve, and `2025-03-26` asks servers to receive JSON-RPC batches, which the server refuses: offering them would promise what is not implemented. |
| Credentials | static bearer tokens: an API token `dvh_pat_...` in `Authorization: Bearer`, minted for a principal with `mcp:read`, `mcp:write` and optionally `mcp:schedule_external`, with an expiry of at most `security.max_mcp_token_days` (90). **MCP OAuth (authorization server metadata, dynamic client registration) is not offered in 1.0**: an operator creates the token for the service principal of the assistant (`POST /api/v1/tenants/{tenant}/api-tokens` with a tenant token that holds `credentials:write`, or `davhaven admin principal-token create`, `docs/operations/runbook.md`) and puts it into the assistant's connector configuration. A wrong, revoked or expired token is `401` with `WWW-Authenticate: Bearer realm="davhaven"`. Only a principal token acts as a person: a tenant or system token can shake hands but is offered no tools, and every call answers `not-found` (it acts as nobody, which is what the permission matrix expects); a principal token without `mcp:read` or `mcp:write` is offered no tools and every call is `forbidden` | A static, scoped, expiring and revocable token is the credential every assistant platform can hold today, and the credential model of PLAN 2.6 already is that. |
| The tenant switch | MCP is **off per tenant until the tenant switches it on** (`tenant.settings.mcp_enabled`, default off). For a tenant that has not, no token with `mcp:*` scopes is minted (`409 feature-not-enabled`, as for feeds) and the endpoint does not authenticate its principals (`404 not-found`: for that tenant it does not exist); switching it off ends the access at once on the instance that made the change and within 5 seconds on the others. `mcp.enabled = false` removes the endpoint for the whole deployment (every path answers 404) | Fail closed: a feature that hands calendars to a model provider must be a decision of the tenant, and the application, which knows the tenant, is where it is enforced. |
| `Origin` | a request without `Origin` (desktop assistants, scripts) passes; with one it must equal an entry of `mcp.allowed_origins` exactly (scheme, host and port), or it is `403` before the credentials are looked at. The `Host` header is never consulted, which is the point against DNS rebinding: the attacker chooses it. No CORS headers are sent, so a page in a browser cannot call the endpoint even from a listed origin; an assistant that runs in a browser reaches the server through its own back end | MCP requires the check, and a rule that trusts `Host` is what a rebinding attack satisfies. |
| Tools | the ten tools of `davhaven-wire` (`docs/contracts/mcp-tools.json`). `tools/list` returns those the token may call (it acts as a person and carries the tool's scope), with `inputSchema`, `outputSchema`, the annotations (`readOnlyHint`; `destructiveHint` on `delete_event`; `idempotentHint` on reads, `update_event` and `respond_to_invitation`; `openWorldHint: false`) and the scope in `_meta["davhaven/required_scope"]`. The `initialize` result carries `_meta["davhaven/tools_version"]`; both vendor members are part of the committed contract. Reads need `mcp:read`, writes `mcp:write`; neither implies the other | A client should offer a model only what it may call; names are stable and changes additive. |
| Results | a success returns `structuredContent` (valid against the `outputSchema`) and the same JSON as one text block. A failure is a tool result with `isError: true`, a short text and **no `structuredContent`**: the problem document of the management API (`type`, `title`, `status`, `detail`, `code`, `request_id`, `errors[{pointer, code, message}]`) is in `_meta["davhaven/problem"]`, beside `_meta["davhaven/retryable"]` (and `davhaven/retry_after_seconds` for rate limits). JSON-RPC errors are for faults of the protocol only: an unknown method (`-32601`), an unknown tool and parameters that do not fit their method (`-32602`). Arguments that do not fit a tool are a failed result (`validation-failed`, naming the member; `""` as the pointer when the whole object is wrong), so the model can correct the call | Every tool announces an `outputSchema`, and the specification requires structured content to conform to it: a client that validates it whenever it is present would turn each failure into an exception of its own, and the model would never see it (ADR-0014 amends PLAN 2.12 here). |
| Acting as the person | every call is made with the context of the token: the same `decide`, the same visibility (what the person cannot see is `not-found`, never `forbidden`), the same scheduling rules, change log, domain events and audit record (`mcp.write`, in the transaction of the write) as DAV and the API. `list_calendars` shows the person's home with the access to each calendar and whether it is `writable` (write access, and not a mirror) | One decision point (PLAN 2.6); nothing about permissions is decided in the protocol layer. |
| What an assistant is shown | text that people wrote (titles, descriptions, locations, calendar names, attendee names) only appears in `untrusted_text` objects and `untrusted_name` members, so a model can tell data from instructions; the server instructions say so, and say that `uid` and `external_key`, which clients choose, are data too. `X-` properties, attachments, alarms, the URL, categories and the organizer's address are never returned (the assistant learns `organizer_is_me`, `my_partstat` and the number of attendees). Attendee addresses come only with `include_attendees: true`. **An event of class `PRIVATE` or `CONFIDENTIAL` in a calendar the person does not own is only the time it blocks** (the start, end, status, transparency, class and recurrence; no text, attendees, organizer or key; its `uid` is the id of the object): the rule of subscription feeds (the class is restricted and the reader is not the owner of the calendar; being organizer or attendee does not lift it, as in feeds), applied by the application to every view MCP gets. It holds for reads, searches and the answers of writes alike, a **text search never matches the text of such an event** (it could otherwise be used to read it, one probe at a time), and **an update of an event the assistant sees as busy time is refused** (`forbidden`; `class: public` or `class: null` would otherwise unmask it), and so is an update that names an instance (`scope` `this` or `this_and_future` with a `recurrence_id`) that reaches a private override of a public series, the instances after it included for `this_and_future`. DAV and the management API show the person's own clients everything the person may read | A calendar is full of strings written by other people, which are the vector of prompt injection, and addresses are personal data (PLAN 2.12). The assistant's provider receives what the assistant reads. |
| Ranges and limits | a time range must end after it starts and is at most `mcp.max_range_days` (92) long; `limit` defaults to the default page of the API limits (`limits.api.default_page_size`, 50), is capped at `mcp.max_results` (200, which must not exceed `limits.api.max_page_size`: `config check` says so; 50 for the slots of `find_free_slots`, whose default is 20) and a `limit` of 0 is read as 1, as the API does. The cursor of a page is the signed cursor of the application and **belongs to the search that made it** (its calendars, range, text and expansion): with other arguments it is refused (`validation-failed` on `/cursor`), and `truncated` means that a cursor exists. `search_events` needs a text of 2 to 200 characters, starts now (the clock of the application) when the call names no start and ends `mcp.max_range_days` later when it names no end; `free_busy` and `find_free_slots` take e-mail addresses of people in the tenant (an address without a scheme is a `mailto:` address) and say `known: false` for addresses the tenant does not know, which principal search over DAV exposes to every member as well | Bounded answers for a model with a bounded context; the same limits for every tool; a cursor carried to another search would skip or repeat results. |
| `create_event` | `summary` and `start` are required. A `client_request_id` is the external key of the event and the UID derives from it. The event is created **once**: a repeated call returns the event of the first one (`created: false`; nothing is written, no entity tag changes, nobody is told), and an id that already names an event with other content, including an event an integration manages through the API under the same key, is a `conflict` that changes nothing. Nobody is notified unless `notify_attendees` is `true`; attendees outside the tenant additionally need the scope `mcp:schedule_external` | A model retries, and it reuses ids: creating twice must be impossible, and so must rewriting an earlier event or mailing by accident. (The API's `PUT …/by-key/{key}` is an upsert; a retried call and a reused key are not the same thing.) |
| `update_event`, `delete_event` | the changes are merged into the stored event as a JSON Merge Patch (what a call does not name is kept, a field sent as `null` is removed; see "JSON event fields"); `if_match` makes the write conditional on the entity tag the assistant read (`precondition-failed` otherwise); `scope` (`this`, `this_and_future`, `all`) with the `recurrence_id` of the instance, which the first two need; a `recurrence_id` of the call replaces one inside `changes`. A deletion of a whole event that is not there answers `deleted: false`, once the application has decided that the person may delete in that calendar: a calendar they cannot see (or that does not exist) is `not-found`, one they may only read is `forbidden`, never a success that did nothing. An instance of an event that is not there, and a stale `if_match` on one, are `not-found` | The call asked for the event to be gone; a denied deletion must still look like a denial (the permission matrix expects it) and must not tell invisible calendars from missing ones. |
| `respond_to_invitation` | `accepted`, `declined` or `tentative` with a comment of at most 500 characters; the person's own `PARTSTAT` changes and the organizer is answered like after a client's write (see Scheduling) | One path for every reply. |
| Budgets | per token, tool calls per minute, in two **buckets of the rate limiter** the deployment chose: `mcp_read` for the tools that read (default 120 per minute) and `mcp_write` for those that write (30). The allowance is the limiter's configuration (`[plugin.rate_limiter.memory.buckets.mcp_read]`, `mcp_write`), and a shared limiter, when there is one, shares it between instances. A call over the budget is a failed result `rate-limited` with the seconds to wait, and costs nothing; a call with arguments that do not fit costs like any other. The listing of tools and the handshake are free. Refusals are counted (`davhaven_budget_refusals_total{class}`) and audited as `rate_limit.tripped`: one record per token, budget and minute when the token trips, and one with the total when a minute with more refusals ends. A limiter that does not answer lets the call through | A model in a loop must not flood a calendar, and reads must not starve writes; the limiter is a port (R2). |
| The present | `search_events` without a start uses the clock of the application, the one the services use (the tests' manual clock reaches it) | The one tool that defaults to now. |
| Logs | the log filter of the server never lets the `rmcp` library log below `info` (a directive appended after `observability.log_filter` and `RUST_LOG`), because the library logs the parsed requests and results, which are titles, descriptions and attendee addresses, at `debug` and `trace`. The server itself logs the tool, the outcome and the request id, never arguments or results | R8: no iCalendar data or addresses in logs. |

## Credentials, authentication and client configuration (PLAN 2.6)

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| Secrets | generated by the server, shown once in the response that creates them, stored as HMAC-SHA256 with a keyed pepper (found by their prefix); responses that carry them are never stored for replay | `ENGINEERING_RULES` R6. |
| Revocation | revoking an app password or a principal's token sets `revoked_at` and moves `credential_generation` of the principal, which ends cached verifications at once; revoking again changes nothing and is not audited a second time. Tenant tokens have no principal and no generation: they stop working when the authenticators' cache entry expires. Feed tokens are looked up on every request. A tenant is remembered for 5 seconds (its status and slug), so a suspension takes effect at once on the instance that made it and within 5 seconds on the others | A revoked password must not work for five more minutes. |
| Credential and surface | an app password works on DAV only, an API or MCP token on the management API and MCP only, a feed token on feeds only; a credential on another surface, or of a suspended tenant, fails like an unknown one (`401`) | A leaked feed URL must not open the API. |
| Failed logins | counted per (login, client address) and per client address in the rate limiter, under keyed hashes (the limiter never sees a login or an address). A client over the limit gets `429` with `Retry-After` before any credential is checked; there is no account lockout, so another address still gets in. A limiter that is down never locks anybody out | PLAN 2.6, R6. |
| Wrong tenant | a valid credential presented for the path of another tenant is authenticated and the request is `404`, like every resource of another tenant; it is no failed authentication and never counts toward the backoff. A credential of a suspended tenant is `401` whatever the path says | R4, ADR 0012: authentication does not decide visibility. |
| Signed profiles | with `[security.profile_signing]` (`certificate_file`, `private_key_file`) the Apple profile is a CMS `SignedData` (DER, the profile inside the signature, SHA-256, RSA PKCS#1 v1.5 or ECDSA P-256) signed with the certificate of the deployment, and iOS and macOS show the name of the certificate and "Verified" instead of "Not Verified" when it chains to a root the device trusts (the TLS certificate of the server will do). Off by default and the certificate is the deployment's, never the software's: the files are read at the start and again about once a minute while the server runs, so a renewed certificate (the files replaced by an atomic rename, as ACME clients do) is picked up without a restart (when the files are reached through a mounted directory: a single-file bind mount, a Compose or Swarm secret and a Kubernetes `subPath` pin the file and need a restart; both settings may name one combined PEM file), a key that does not belong to the first certificate stops the start and `davhaven config check`, and an encrypted key is refused. A new pair that cannot be used while the server runs (a key that does not belong to the certificate, a damaged file, a certificate that has ended) is a warning in the log and does not replace the pair in use. A certificate that has run out, or runs out within 14 days, is a warning of `davhaven config check` and of the start, and `davhaven_profile_signing_certificate_expiry_timestamp_seconds` says when the certificate in use ends. The media type and the file name stay what they were | An unsigned profile installs but looks untrustworthy to the people asked to install it. `docs/configuration.md` has the keys. |
| Client configuration | `generic` has no secret and no side effect; the Apple profile and the DAVx5 login mint an app password with the label of the request. The profile identifier is `{prefix}.caldav.{principal id}` (the tenant's `client_config.apple_identifier_prefix`, else the reversed host of the server), so installing a profile again replaces the account. A profile with a feed mints the app password and the feed token in one transaction, after checking that the tenant has feeds and the calendar is readable, so a profile that fails leaves no password whose secret nobody saw; a tenant without feeds answers `409 feature-not-enabled` | PLAN 2.10. |
| Audit records | a record names the actor by kind and id, the label of the credential it used and a keyed hash of the client address bound to the tenant (the same address has another hash in every tenant). Events for webhooks and the outbox carry the actor's kind and ids but neither the label nor the hash | Operators need the label; third parties do not. |

## Feeds (PLAN 2.13)

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| Content | the master events and overrides of the token's calendars within the window (`feeds.window_past_days` before and `feeds.window_future_days` after the start of the current UTC day, so the window moves once a day); `X-WR-CALNAME`, `REFRESH-INTERVAL` and `X-PUBLISHED-TTL` carry `feeds.refresh_interval`; every `TZID` has one `VTIMEZONE`, the object's own or, for zones of the database, one rendered for the window. A feed holds at most `feeds.max_objects` (20 000) objects and `feeds.max_bytes` (32 MiB) of calendar data and is cut after them, not failed; it is rendered in chunks of 200 objects on blocking threads, each with its own time budget. Folded content lines and `TZID` parameters with quoted colons are read as the iCalendar grammar says | Subscribers refresh at the interval the operator chose; a `TZID` without a definition is read as floating time by some of them. |
| Busy mode | start, end, rules and exceptions only; the summary is the text the tenant named for the language of the feed's owner (the principal's language, else the tenant's): `busy_text_by_locale` of its settings is a map from language tag to text, looked up as the tag is and then without its last subtag (`de-AT` finds `de`), and `busy_text` is one text for every language that answers where the map names none; where the tenant named neither, the `feed_busy` template in that language (plain "Busy" where there is no template). The UID is a keyed hash that differs per token, transparent and cancelled events are left out | Nothing a person wrote may reach a feed that others can subscribe to. |
| Entity tag and `304` | the strong `ETag` is derived from what the document is made of, not from its bytes: the calendars' sync epoch, sequence number and version, who reads them, the mode, the localized busy text, the name, the window, the limits and the build (the version and the revision of the release, and the version of the time zone database that the `VTIMEZONE` components come from). `If-None-Match` with the current tag is answered with `304` before any object is read or rendered, after the access has been checked; the tag changes whenever the document does, at midnight UTC when the window moves and with every release | A subscriber that polls every few minutes costs a few small queries instead of the parsing of a year of events. A release that renders a feed differently must not be answered with `304` for the bytes of the one before, so every subscriber reads its feed once after an upgrade. |
| Restricted events | `CLASS:PRIVATE` and `CLASS:CONFIDENTIAL` are busy-only for everybody but the owner of the calendar, in every mode | PLAN 2.13. |
| Access | checked again on every request with the principal of the token, before the entity tag is compared: a calendar the principal can no longer read drops out of the feed, and a feed with none left, a revoked token, a deleted calendar, a suspended or deleted principal and a tenant that turned feeds off all answer `404` | A feed URL is a bearer secret; losing access must end it. |

## Mail (RFC 6047, iMIP)

`docs/mail.md` describes the mail itself; these are the choices that depend on how other systems behave.

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| `From` of invitations and cancellations | `"{organizer} via {tenant}" <noreply@{sender domain}>`, `Reply-To` the organizer (`mail.from_mode = service`, the default); `organizer` mode puts the organizer's own address in `From` only for people in the tenant's sender domain | The relay signs for the sender domain only. A message from a foreign domain without DKIM alignment fails DMARC and lands in spam, which is worse than a sender name that says "via". |
| `From` of a `REPLY` | the same service form: `"{attendee} via {tenant}"`, `Reply-To` the attendee | **A known limitation.** RFC 6047 and the scheduling code of several clients expect the sender of a `REPLY` to be the attendee, and a receiver that checks it may not apply a reply it receives from the tenant's address. `davhaven_mail_reply_service_form_total` counts the replies that went out this way. Operators whose users have addresses in the tenant's sender domain set `mail.from_mode = organizer`: their replies then come from their own address. The RSVP link does not depend on the sender at all. |
| `DTSTAMP` of a message | the moment the job was queued, not the moment the mail is sent | A retry then says the same thing, and a `CANCEL` queued after a `REQUEST` is never older than it (RFC 5546 section 2.1.5). |
| Attendees shown | the recipient's own `ATTENDEE` line only, in the iCalendar part and in the mail text | Guests learn nothing about who else is invited (see Scheduling below). The template model has no list of attendees. |
| Invitations that were overtaken | an invitation whose recipient is no longer an attendee, or whose `SEQUENCE` is lower than the stored object's, is dropped when it is sent | Outbox records are not ordered; the cancellation or the newer invitation that made it obsolete is queued on its own. |
| Answers by mail button | reach the organizer's mailbox and change `PARTSTAT` only if a gateway forwards them to the inbound iTIP endpoint | There is no mailbox the server reads. The RSVP link is the tracked path. |
| `COMMENT` of a `REPLY` | the attendee's remark, cut at 500 characters, in the calendar part and in the mail text | RFC 5546 section 3.2.3. |
| Where replies go, in the footer | the mail model has `reply_to`: the address a reply reaches a person at (the `Reply-To` of the service form, or the `From` of `organizer` mode), `null` when the mail comes from the tenant's no-reply address because the person has no address of their own (a service account). The default footers say where replies go, or ask not to reply, by it, and a theme writes its own words | A footer that says "reply to this message" over a mail nobody reads is worse than none. |
| The organizer in the calendar part | an organizer without a mail address (a service account is known by an `urn:uuid`) is named in the `REQUEST` and `CANCEL` by the tenant's sender address, with the name of the event's `CN`; the stored event keeps its own organizer | A guest's mail client cannot use an `urn:uuid`. Replies by mail button go to the no-reply address and change nothing (see above); the RSVP link is the tracked path. A gateway that forwards such a reply to the inbound iTIP endpoint has it quarantined as `unknown_event` (`scheduling.reply_rejected`): the address names no principal, so the organizer copy cannot be found by it. |

## Scheduling (RFC 5546, RFC 6638)

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| Who writes the answers | `PARTSTAT` and `SCHEDULE-STATUS` of attendees on the organizer's copy are the server's: only a `REPLY` changes an answer, only delivery writes a status. Whatever the organizer's client sends is replaced by the stored value, or `NEEDS-ACTION` for an attendee that is new on the instance | PLAN 2.8 and RFC 6638: anyone who can write the organizer's calendar (a group-calendar member, an API or MCP caller) could otherwise forge an acceptance, and a stale copy would overwrite a reply that arrived after the client read it. |
| Significant changes | `DTSTART`, `DTEND`/`DURATION`/`DUE`, `RRULE`, `RDATE`, `EXDATE`, `LOCATION`, `SUMMARY`, `STATUS` reset the answers of the instance to `NEEDS-ACTION` and raise its `SEQUENCE`; other edits update internal copies silently and send nothing | PLAN 2.8. RFC 5546 section 2.1.4 gives examples and leaves the rest to the implementation. |
| A moved single instance | a new override that moves, shortens or renames its instance is a significant change of that instance | It is compared with the instance the series produced. |
| `DTSTAMP` and `SEQUENCE` of a message | every component carries the `DTSTAMP` of the moment the message is built; `SEQUENCE` is that of the copy it is built from | RFC 5546 section 2.1.5 orders messages with equal `SEQUENCE` by `DTSTAMP`; a `CANCEL` that kept the stamp of the invitation could be ignored as not newer. |
| Attendees shown in `REQUEST` and `CANCEL` | the recipient's own `ATTENDEE` line only (`AttendeeVisibility::Own`, the default); `AttendeeVisibility::All` lists everybody | Google and Outlook list all guests. Guests learn nothing about who else is invited from the message or from an internal attendee's copy, which is the privacy-preserving default; the application may choose `All` per tenant. |
| An attendee removed from one instance | gets the rest of the series and an instance `CANCEL` for that instance; components that do not list the recipient are left out of a message | An override may name other attendees than the series. |
| `CANCEL` of a series | the master component alone, `STATUS:CANCELLED` | RFC 5546 section 3.2.5. |
| `REPLY` | carries the replying attendee only, the properties the organizer needs, and the attendee's `COMMENT`, which the organizer's copy keeps as an `X-CALENDARSERVER-ATTENDEE-COMMENT` of the answered component (naming the attendee in `X-CALENDARSERVER-ATTENDEE-REF` and the reply in `X-CALENDARSERVER-DTSTAMP`, one per attendee, replaced by the attendee's next answer and removed by an answer without a remark), where Calendar on macOS shows it next to the guest, and which no other attendee is ever sent in iTIP. The comment is the server's like the answer it belongs to: a write of the organizer's copy drops the comments a client sends and keeps the stored ones of the attendees that keep their answer, and a significant change that resets an answer takes its comment away. It stays on the organizer's copy, so **everybody who can read that copy sees it** (members of a group calendar, sharees, the other attendees who read a team calendar); a subscription feed leaves it out | RFC 5546 section 3.2.3. The replying attendee comes from the request context, never from the body: `apply_reply_with` refuses a reply that names another attendee than the one who sent it. |
| A reply without `RECURRENCE-ID` | answers the series: the master and every override that still carries the attendee's earlier answer; an override the attendee answered differently keeps that answer | RFC 5546 reads such a reply as the whole recurrence set. |
| Addresses on the wire | principal URLs and `urn:uuid` addresses are mapped to `mailto` before a message is built (`itip::rewrite_addresses`); `SCHEDULE-*` parameters are stripped | PLAN 2.6. Other systems cannot resolve a principal URL of this server. |
| Attendees scheduled by their client | an attendee with `SCHEDULE-AGENT=CLIENT` (or `NONE`) is not scheduled by the server (PLAN 2.8) and keeps the answer the client wrote | RFC 6638 (`SCHEDULE-AGENT`). |
| Inbound messages | held to the rules of stored objects: dates, rules, counts, sizes, one UID, only the components the `METHOD` allows | The inbound endpoint is an internet-facing surface. |

### Server-side scheduling (PLAN 2.8, 2.13)

How the server schedules when an organizer writes, an attendee answers or a gateway forwards mail. The iTIP
building blocks above are used as they are; these rows are the decisions of the application. The decision table that
the scheduling matrix runs is `crates/it/tests/scheduling/table.rs` (see `docs/testing.md`).

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| Who schedules | A `PUT` schedules when the `ORGANIZER` is one of the writer's addresses, or one of the calendar owner's while the writer has `ReadWrite` access to that calendar; then every message names the writer as the sender (`ORGANIZER;SENT-BY`). A writer with `ReadWrite` access to somebody's calendar answers for the owner as well when the owner is an attendee. In a group calendar the member is the organizer; nobody organizes in the name of a group, so **only the organizer changes or deletes a meeting in a group calendar** (403 `CALDAV:allowed-organizer-scheduling-object-change` for another member). An `ORGANIZER` never changes on an existing meeting (the same 403), and an object that names another principal of the tenant as organizer is refused (403 `CALDAV:organizer-allowed`) whether it is new or was written as a plain event first. An event that names nobody of the writer, in a calendar the writer controls, is stored as it is and nothing is sent. A write that is stale by `ETag` but current by `Schedule-Tag` is merged for the organizer and for an attendee and is a 412 for everybody else | PLAN 2.8, 2.7. A colleague can type an event into somebody's calendar without becoming its organizer, and nobody can send an invitation in somebody else's name. |
| What is never scheduled | Managed and mirror calendars, to-dos and journal entries, attendees with a `SCHEDULE-AGENT` other than `SERVER`, batch writes, and writes through the API or MCP unless the caller says `notify_attendees` (deletes: `notify_attendees` as well). A caller who says it and acts as nobody (a tenant token) is refused with 422: invitations are sent in the name of a person, so they need a principal token. Through MCP, attendees outside the tenant need the scope `mcp:schedule_external` | Machine writes must not mail people by accident; an MCP caller that can mail outside the organisation needs its own scope (PLAN 2.12). |
| Classification of an address | A user or service principal of the tenant is *internal*, a resource of the tenant is a *resource*, a group (or `CUTYPE=GROUP`) is a *group*, a mail address nobody in the tenant owns is *external*, **including the addresses of other tenants**, and a principal URL or `urn:uuid` that names nobody here, or an address a deleted principal still holds (reserved until the purge), is *unknown*. Groups and unknown addresses get `SCHEDULE-STATUS` 3.7 and nothing else | Tenants are isolated: a principal of another tenant is reached by mail, like anybody outside. Groups are not expanded in 1.0 (`docs/ROADMAP.md`). |
| Internal delivery | In the organizer's transaction, after the calendar of the write was locked, with the calendars of the copies that change locked together in ascending id order: the message goes into the attendee's scheduling inbox and, by policy, a copy of the event into their default calendar (`SCHEDULE-STATUS` 1.2). A recipient who sees the organizer's calendar already (owner, member of its group, accepted grant, directly or through a group) gets the inbox item only (`scheduling.suppress_duplicate_copies`, on by default): this follows effective access, not the bindings of the recipient's home, which are created when they first list it. The replacement of an existing copy keeps the attendee's own alarms and `TRANSP` (PLAN 2.8 lets them change exactly these), so an edit of the organizer, a silent one as well, never deletes their reminders. **A delivery acts only on a copy the same organizer sent**: a recipient who has an event with another `ORGANIZER` under the `UID` (their own meeting, a meeting of a third person that they attend, a booking of somebody else) is skipped: nothing of theirs is replaced or removed, nothing is put into their inbox, and the organizer's copy says `5.1` for them. An older `SEQUENCE` is never delivered over a newer one | PLAN 2.8: a group calendar must not show the event twice. A `UID` is not a secret (every attendee sees it), and it must not be a way to overwrite or delete somebody else's calendar object. |
| Above the cap | Internal attendees beyond `scheduling.max_sync_internal_attendees` (50) are queued as one `internal_delivery` outbox record per kind of delivery (`REQUEST`, `CANCEL`, and `REQUEST` with `copy_only` for an edit that is not significant) and delivered by the dispatcher (`SCHEDULE-STATUS` 1.0). The record carries a snapshot of the organizer's copy, the inbox items are named after the record and the recipient (a record handled twice delivers once), the ownership rule above applies when it is handled, and a recipient who is suspended or no longer an attendee in the meantime is skipped. The organizer's copy keeps `1.0`; it is not rewritten when the delivery is made. A queued recipient whose only change is a cancelled instance gets the updated `REQUEST` (the `EXDATE` in it says the same), not the `CANCEL` of the instance that an attendee within the cap gets. The handler of the kind is part of every dispatcher the application builds (`outbox::handlers`) | The organizer's transaction must stay short, and rewriting the organizer's copy after the fact would change what the organizer's client sees without a change of the organizer. |
| A change of an event | The messages and copies of the iTIP golden set apply (significant: `REQUEST` to everybody; new attendee: `REQUEST` to that one; removed attendee: `CANCEL` of the whole object; insignificant: no message, the copies follow). A cancelled instance (`EXDATE`) gives internal attendees the updated `REQUEST` and a `CANCEL` of the instance; **external attendees get the updated `REQUEST` only**, because the iMIP composer builds whole-object messages and the `EXDATE` in the update says the same | The golden messages are exact for the inbox; a mail client applies the updated series. |
| Moving between calendars | `MOVE` within one owner is a relocation: no message, the `Schedule-Tag` and the links stay | PLAN 2.7. |
| An attendee's copy | The attendee may change their own `ATTENDEE` parameters (`PARTSTAT`, comment), alarms and `TRANSP`; anything else, including adding attendees and removing their own line, is 403 `CALDAV:allowed-attendee-scheduling-object-change`. A write that is stale by `ETag` but current by `Schedule-Tag` keeps the stored copy and takes over the answer instead of answering 412. Deleting the copy answers `DECLINED` unless `Schedule-Reply: F` | PLAN 2.8, 2.7. The `REPLY` always names the attendee the request context says, never the one in the body. |
| Answers | Every answer (a client, the RSVP page, a gateway) is folded into the organizer's copy by one processor under the lock of its calendar. The `Schedule-Tag` of the organizer's copy does not change, an answer that repeats the stored one tells nobody again unless it comes with a remark, and an answer to one instance changes that instance. The organizer is told through the scheduling inbox (`REPLY`) and `scheduling.reply_received`. The organizer's copy is the one in a calendar the organizer owns; failing that the only one in a group calendar or a calendar shared with write access: two candidates are ambiguous and the answer stays in the attendee's copy | A server merge must not make the organizer's client believe the event changed; two answers that arrive together both count. |
| Answering through the API or MCP | `respond_to_invitation` changes the caller's own `PARTSTAT` and sends the `REPLY` like a client's write does. A caller who sees the event but is not one of its attendees (the organizer, a colleague, a tenant token) is refused with 403; an event the caller cannot see is 404. The remark (500 characters) travels with the answer, and a repeated answer with a new remark still reaches the organizer. An answer to an organizer outside the tenant is mail, so over MCP it needs `mcp:schedule_external` and counts against the quotas | The event is the caller's to read, not to answer; PLAN 2.12. |
| An organizer outside the tenant | A principal's answer to an event that somebody outside the tenant organizes goes out as an iMIP `REPLY` (the remark as `COMMENT`), subject to the tenant's external policy | PLAN 2.8. |
| Resources | A resource answers a booking by itself through the scheduling policy: the default accepts when the resource is free for every instance (the end of a booking is exclusive; the event's own copy does not count) and declines when it is not, and a declined booking is not added to the resource's calendar. The `manual` policy never answers and never adds invitations to calendars; a deployment can register its own policy | PLAN 2.8 ("Policy hook"). |
| External mail | Per tenant `scheduling.external` (`allow`, `allowlist`, `deny`); mail to a refused address is not sent and the organizer's copy says `5.1`. Limits never refuse a write and never block a cancellation: `scheduling.external_per_event` (50) outside recipients of one event (the first 50 in the order of the attendee list are mailed, the others are not and say `5.1`), `external_per_organizer_per_hour` (100) and `external_per_tenant_per_day` (1000) count **invitations** (a `REQUEST` to somebody outside), and a recipient beyond the allowance is not mailed and says `5.1`. The write itself is stored, and its other recipients are written to as usual. Cancellations are exempt: they go to the same recipients an invitation went to and are not counted. An answer an internal attendee sends by mail to an organizer outside the tenant (`REPLY`) is held to the same controls: the external policy, the quotas (the answering person is the sender; over the limit the answer is refused with 429 and `Retry-After` and stored nowhere) and, over MCP, the scope `mcp:schedule_external`. The quota is charged when the object is stored and the mails are queued, so a write that fails or is retried uses up nothing. The counters live in the memory of the process (one instance per database, PLAN 1.1; `docs/ROADMAP.md`) | PLAN 2.8, 2.12. A calendar client does not expect a 429 on a `PUT`, and delivery state is what `SCHEDULE-STATUS` is for. |
| Free-busy | Open to every principal of the tenant and to nobody else. It says when somebody is busy and never why: private and confidential events count, transparent and cancelled ones do not, `STATUS:TENTATIVE` is `BUSY-TENTATIVE`. The time of a person is the time of the calendars they own and of the managed calendars they see, except hidden ones and those marked transparent for scheduling, **and the meetings they organize or attend** (an `ATTENDEE` whose `PARTSTAT` is not `DECLINED`, on the master or on one instance) in the calendars of the groups they belong to and in the calendars shared with them (accepted grants, directly or through a group). The calendars a person sees follow from membership and grants, not from the bindings of their home (those are created when they first list it), so the answer does not depend on whether their client ever listed the home. Principals of other tenants, groups and strangers are answered as unknown, without periods. Ranges must be bounded and at most 10 years | PLAN 2.6, 2.15. A meeting in a group calendar is the member's time as much as one in their own. |
| Free slots | The search for times when everybody is free returns slots on a quarter-hour grid (UTC), earliest first, optionally inside working hours of a time zone (the caller's, else the tenant's); the answer says when more slots exist than were asked for | MCP `find_free_slots`. |
| Outbox and inbox | `POST` to the outbox takes one `VFREEBUSY` `REQUEST` of the owner of the outbox and answers with one entry per attendee: the busy time of a person of the tenant as a `REPLY` with a `VFREEBUSY` and the request status `2.0;Success` (the DAV layer writes it for `ScheduleStatus::Delivered` in a `schedule-response`), status 3.7 for everybody else. Invitations are not posted, they happen when the organizer's copy is written. The inbox is its principal's alone: nobody else, not even the organizer or another tenant, can list, read or delete in it, and quarantined messages are never shown | RFC 6638 section 5; PLAN 2.8. |
| RSVP page | `GET` renders the invitation (summary, time, location, the organizer's name; never the description, other attendees or an address) with a form that posts to the address of the page itself (`action="?"`: the application never holds the link). The answer becomes the same iTIP `REPLY` as any other, so it reaches the organizer's copy, inbox and events in one transaction, and the use of the link is recorded. A form that cannot be used (the CSRF token is wrong or older than an hour, the answer is none of the three, the remark is longer than 500 characters) records nothing and shows the form again, with a fresh token and a notice (`invalid_csrf`, `invalid_answer`, `comment_too_long`), as the page itself with status 200. A link that was revoked or expired meanwhile answers like an unknown one. The link of an update is the link of the invitation while it outlives the event; when the event moves later a second link is minted and the first keeps working until its own expiry (ADR-0007) | PLAN 2.13. |

#### Inbound iTIP (`POST /api/v1/tenants/{tenant}/itip/inbound`)

Off by default (`scheduling.inbound_itip.enabled`); the caller needs the scope `itip:inbound` (checked before anything
else is said about the feature). A message that fails a check is **quarantined**: one copy of it is kept in the
scheduling inbox of the person it was meant for (the organizer for a reply, the first attendee in the tenant for an
invitation; a message that names nobody in the tenant is not kept, there is nobody it was meant for), flagged so that no
client ever sees it, `scheduling.reply_rejected` is emitted for replies and the audit log says why. The gateway gets
`200` with `outcome: quarantined` and the reason, so it does not retry what can never be applied.

Messages are deduplicated on `Message-ID`, whether anything was kept or not: the first time a message is dealt with the
server records its `Message-ID` as an idempotency key of the calling token for 24 hours, in the same transaction, and a
repeat answers `duplicate` without emitting a second event or writing a second audit record. Messages are rate-limited
per sender (the bucket `itip_inbound`, keyed by `From`) and per gateway (`itip_inbound_gateway`, keyed by the token that
forwards them: the sender of a mail is unauthenticated, so a limit per sender alone is dodged by varying `From`), both
429 with `Retry-After`; tune them under `[plugin.rate_limiter.memory.buckets]`. A limiter that does not answer refuses the message
(503) instead of letting it through.

| Reason | When |
| --- | --- |
| `dmarc_not_passed` | the gateway did not report a DMARC pass (unless `scheduling.inbound_itip.require_dmarc_pass` is off) |
| `method_not_supported` | the `METHOD` is none the endpoint takes: only `REPLY`, `REQUEST` and `CANCEL` can be forwarded |
| `method_not_enabled` | the tenant accepts `reply` only unless `scheduling.inbound_methods` lists `request` or `cancel` |
| `sender_mismatch` | `From` is not the replying `ATTENDEE` (for an invitation or cancellation: not the `ORGANIZER`) |
| `internal_attendee` | the reply is for a person of the tenant: they answer in their calendar, and a mail that says it is from them proves nothing |
| `unknown_event`, `unknown_attendee` | the `UID` names no organizer object of the tenant, or the attendee is not on it; an invitation whose recipients all have an event of somebody else under the `UID` is `unknown_event` as well |
| `sequence_mismatch` | the answer is about another version of the event than the organizer's copy |
| `organizer_is_internal` | an invitation or cancellation that claims a principal of the tenant as organizer |
| `no_internal_recipient` | an invitation or cancellation that names nobody in the tenant |
| `invalid_reply` | the reply does not fit the copy, or does not have exactly one organizer and one attendee |
| `invalid_message` | an invitation or cancellation without a `UID` or an `ORGANIZER` |
| `unsupported_component` | the message is not about an event |
| `content_rejected` | a content scanner refused an inline attachment of an invitation (a scanner that does not answer fails the request with 503: content that was not scanned is not stored) |

Invitations and cancellations from an organizer outside the tenant (when enabled) are delivered to the attendees
inside it with the same delivery as an internal organizer's (so only to copies that organizer sent, and an invitation
that is older than what the attendee has is dropped). The copy the attendee gets is the object of the message without
the alarms of the sender, which are not the attendee's to have fire on their devices.

## Authentication (RFC 7617, RFC 6750)

`docs/api.md` describes the management API's use of tokens; these are the choices that depend on how clients behave.

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| Challenge | DAV answers 401 with `WWW-Authenticate: Basic realm="{tenant}", charset="UTF-8"` (the tenant of the path, `davhaven` when the path names none); the API and MCP answer `Bearer realm="davhaven"`. `OPTIONS` on DAV is answered without credentials | Clients show the realm in their login prompt, and `charset="UTF-8"` makes them send UTF-8 (RFC 7617). Capability discovery must work before a login exists. |
| Login | `name@login_domain`, or the bare name when the path names the tenant (then it means "this name in that tenant"). An app password is accepted only for the login of its owner; any other login is an unknown credential | DAV clients discover the account from a login typed by a person, and a stray password must not open another account. |
| Another tenant's path | a valid credential is authenticated whatever tenant the path names, and the application answers 404 for the path, like for every resource of another tenant (R4, PLAN 2.6). That attempt is not a failed authentication and does not count for the backoff | The path of another tenant is a resource the caller cannot see, not a wrong password: answering 401 would tell a client with a good credential that it is wrong, and would let it be blocked with it. |
| App passwords | nine groups of four lowercase base32 characters (180 bits); the first two groups are the prefix that finds the credential (stored and listed in clear), the other seven (140 bits) are the secret that is hashed, which is at least the 128 secret bits that R6 asks of every credential. The case of the letters and surrounding whitespace do not matter, a missing or extra group does. Accepted on DAV only, and only for the login of their owner | People type them, and a trailing space or a capital letter from a keyboard should not be a failure. A stray password must not open anything else. Guessing the secret is bounded by the failure backoff, not by its length alone. |
| Tokens | `dvh_pat_`, `dvh_feed_` and `dvh_rsvp_` followed by 12 prefix characters, `_` and 43 secret characters. API tokens work on the API and MCP in the `Authorization: Bearer` header only, feed and RSVP tokens in the URL of their page only | A value carrying a marker of ours is judged by us (and refused when malformed or on the wrong surface); secret scanners and log filters find the markers. |
| One format, one owner | the markers, lengths, alphabets and the splitting into prefix and secret live in `davhaven_domain::credential_format` (`AppPasswordText`, `TokenText`). Whoever mints a credential (the application, the fixtures, the RSVP derivation) and whoever verifies it (`auth-local`) use that module, and a test of each drifts when the format does | A format that is written out in four places is a credential that mints and does not verify the day one of them changes. |
| Every refusal is the same | an unknown prefix runs a verification of the same cost as a real one; unknown, wrong, revoked, expired and suspended credentials answer alike | Response time and body must not say which prefixes exist or which accounts are suspended. |
| Cache | a verified app password or principal token is remembered for 5 minutes under an HMAC of the presented secret. The cache saves the hash verification only: every use reads the credential row, the status of its tenant and principal and the principal's `credential_generation` in one query (the same one that finds a credential the process has not seen), so revoking a credential, suspending a principal or a tenant and deleting a principal apply at once, and a hit costs exactly one read like a miss. An entry is valid only for the stored hash it was verified against. A credential whose tenant or principal cannot be found is refused (nothing is assumed active). Failures are never cached; tenant, system, feed and RSVP credentials are verified against the store every time. The cache is bounded (`cache_max_entries`: when it is full, expired entries go first, then the least recently used ones down to nine tenths of the limit, so a full table does not sweep itself for every insert) | DAV clients poll many times a minute; the cost of a request must not depend on a password hash, and revocation must not depend on anyone remembering to bump a counter. |
| `last_used_at` | written at most every 15 minutes per credential, in batches, by a worker | A polling client must not turn into a write per request. |
| Failures | no lockout. Failures per login and client address and per client address back off exponentially (429 with `Retry-After`): a few free failures per window, then blocks of `base`, `2 × base`, … up to `backoff_max`; failures of a blocked key do not extend its block; failures are forgotten after the window (at least as long as the longest block, so the maximum is reachable). The policy is that of the rate limiter, not of the authenticator: the `RateLimiter` port defines the two failure buckets and its contract suite checks them. `[security.auth]` (`backoff_free`, `backoff_window`, `backoff_base`, `backoff_max`) is the one place a deployment sets the numbers, and the server hands them to the limiter in the plugin context; an entry for either bucket under `[plugin.rate_limiter.memory.buckets]` overrides it (the kind is part of the table, because `memory` is also a store and a mail transport) | A lockout lets anyone who knows a login deny service to its owner; a backoff only slows guessing. |
| IPv6 clients | counted by their /64 prefix in both failure buckets (`davhaven_ports::bucket_address`; an IPv4-mapped address is the IPv4 address it maps) | One subscriber controls a whole /64; counting single addresses would let one client mint an endless supply of fresh keys. |
| Pepper rotation | credentials are hashed with a keyed hash under the pepper of the key ring and carry the id of that key (`pepper_kid`). Retired keys stay in `[security] keys` and keep verifying what they made. A credential that is **used** after a rotation is hashed again under the active key, once: the authenticator does it after a fresh verification (never after a cached one), the store swaps the hash only while it still names the old key (`CredentialRepo::rehash`, so two requests cannot undo each other and nothing else of the credential changes), and a failure is logged while the request succeeds. While the instances of a rolling change of `security.active_key_id` disagree on the active key, a used credential can move between the two keys more than once (each move is a compare-and-set that succeeds): harmless, and over when the rollout is. A retired key can be removed when no live credential names it any more (`docs/operations/keys.md` has the query): the credentials that nobody used since the rotation, and system tokens (they belong to no tenant and are not moved), are the ones that depend on it | The plaintext of a credential exists only while a client presents it, so that is when it can be moved. A retired key must not be the permanent price of one rotation, and a credential in daily use must not have to be reissued. |
| Client address | the peer address, or the rightmost `X-Forwarded-For` entry that is not in `server.trusted_proxies`, and only when the peer is a trusted proxy | A client must not be able to choose the address its failures are counted under. |
| Logs | tokens in paths are redacted before any log line (`/feeds/dvh_feed_<redacted>.ics`), route templates are the metric labels, and `Authorization` and cookies are marked sensitive | Feed and RSVP tokens are credentials that travel in URLs. |

## Calendar providers: Google and Microsoft (PLAN 1.1, ADR-0016)

A tenant administrator connects an account at Google or Microsoft for a user; Davhaven copies the primary calendar of the account
into a read-only **mirror calendar** of that user. 1.0 only reads: nothing is ever written to the provider, and the OAuth client asks
for read access to calendars (`calendar.readonly` at Google; `Calendars.Read` at Microsoft, with `offline_access` for the refresh token and `User.Read` to name the account) and nothing else.

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| Off by default | both providers are in the image and off until `[providers.<name>] enabled = true`, a client id and a client secret file are set and `plugins.providers` selects them. A provider that is off answers `409 feature-not-enabled` to `POST …/external-accounts`, is listed with `enabled: false` and has no sync worker. `GET …/providers` lists the providers of the project whether or not the build has them, so the API does not change with the build | A deployment without OAuth clients must not run, or offer, anything of this. |
| The flow | `POST …/external-accounts {provider, principal}` (scope `providers:manage`) answers `{authorization_url}`, which the administrator gives to the person. The consent URL carries a single-use `state` (valid for ten minutes, bound to tenant, principal and provider) and a PKCE `S256` challenge; the verifier stays with the server, sealed. The person consents at the provider, which sends the browser to `GET /oauth/{provider}/callback`; the page that answers says that the calendar is connected or that the connection failed, and never why | The callback has no session. Whoever holds the URL cannot connect an account to another principal, and cannot connect one at all after ten minutes or twice. The URL itself is a short-lived **capability**: whoever opens it first and consents attaches the provider account they consent with to the named principal's mirror, so it goes to that person only, is never logged or forwarded, and the API answers it with `Cache-Control: no-store`. |
| What a connection creates | in one transaction the **mirror calendar** (kind `mirror`, `Provider: account` as its name, the color of the remote calendar when it has one, VEVENT only), the owner's binding to it and the account with its sealed tokens; the connection is audited (`external_account.created`) and the calendar is announced like any new calendar (`calendar.created`). The same account of the same person connected again keeps its account and replaces the tokens, keeps its mirror or, when that is gone, makes a new one: that is the way back from `disabled` and from `mirror_missing`. If a worker claims the account at the same moment, the update is read and tried again, and the tokens of a connection that could not be stored are given back to the provider only when no account holds the grant (at Google, revoking one token ends the whole grant of the person to the client, including the refresh token of an account that is connected already). A person can have several accounts, each with a mirror | The mirror is a calendar like any other for clients, feeds and MCP: it needs no code of its own. |
| Read-only for everybody | DAV (`403 need-privileges`), the API and MCP refuse writes to a mirror, whatever the actor's access is, and a mirror cannot be shared or have its grants changed through the API. A mirror cannot be deleted on its own through the API either (`403`, for every actor; DAV refuses for lack of the privilege): it goes with its account (`DELETE …/external-accounts/{id}`), because an account without its mirror has nothing to pull into. Only the sync engine writes to it | A change made in a client would be lost at the next pull. |
| What is mirrored | the events of the primary calendar of the account (the default calendar, at Microsoft) within a window around today (`history_days`, `future_days` of the provider's table: 90 and 365 days by default), at Google one iCalendar object per series with its overrides and cancelled instances, at Microsoft one object per occurrence (Graph lists the occurrences of the window and not the series); all-day events, `TRANSP` and `CLASS` are kept, and so is the time zone as far as the provider names it: Google names the zone of every event (`TZID`), while Graph answers in UTC unless the request asks for another zone, which the import does not do, so a Microsoft event arrives in UTC. Every pull lists the window again, so **an event that leaves the window leaves the mirror** (a snapshot is complete only within the window). A calendar with more than 10 000 events in the window is not imported (`too_large`) and is not read twice for it. Not mirrored: other calendars, tasks, birthdays, attendees, organizers, alarms, attachments and conference data | Reminders, invitations and replies belong to the provider; mirrored events must never schedule or mail anybody. |
| Time zones in mirror objects | the Google objects name their zones as `TZID=Europe/Berlin` (and likewise for `EXDATE` and `RECURRENCE-ID`) and carry **no `VTIMEZONE`**, although RFC 5545 section 3.2.19 asks for a definition of every `TZID`. They are stored and served as they are (DAV `GET`, multiget, the API's iCalendar output). **A documented deviation**: Davhaven resolves the identifier against its own time zone database when it reads (expansion, free-busy, feeds, which render a `VTIMEZONE` of their own for every zone), and a client that cannot resolve an IANA name reads such a time as floating time | The zone of an event is what the provider says it is; adding observances to every object would store data the provider did not send, and a recurring series would need them for ever. |
| Pulling | every 15 minutes per account (`[providers.sync] interval`), at most `batch_size` accounts per pass and `concurrency` at a time, each under `timeout`. A pull that changes nothing writes nothing (no `ETag`, no sync token change). Several instances share the work: an account is claimed with a lease in its `sync_state`, and a pull that dies is taken up again when its lease runs out | Providers throttle clients that poll often; clients of the mirror see changes within the interval. |
| Failures | `auth_revoked` switches the account off (`status: disabled`), and **only** a refresh token that the provider calls invalid does (RFC 6749 section 5.2 `invalid_grant`: the person removed the access, or it was revoked or expired), or an account with no refresh token. A provider that refuses the **client** of the deployment (`invalid_client`, `unauthorized_client`, `invalid_request`, `invalid_scope`: a wrong, rotated or expired client secret, which Microsoft client secrets do after at most 24 months) is a fault of the deployment and of no account: every account fails with `internal`, nobody is switched off, and the accounts are on again by themselves once the secret is fixed. `provider_rejected`, `provider_unavailable`, `too_large`, `mirror_missing` and `internal` set `status: error` and are tried again after a wait that starts at a third of the interval and doubles up to `backoff_max`. `mirror_missing` means that the mirror calendar is gone (the API does not delete one; a purge or an operator's statement did): the provider is not asked and the person's tokens are not used until the account is connected again, which makes a new mirror, or disconnected. `too_large` means more than 10 000 events in the window: narrow `history_days` and `future_days`. An account whose principal was **deleted** is switched off at its next claim with `last_error` starting `principal_deleted` and its access is given back; that is no failure of a pull and emits no `external_account.sync_failed` (the deletion is audited). The accounts of a suspended principal are left alone and pulled again when the principal is active. A success sets the status back to `active`. `last_error` names the reason in a fixed sentence, never the provider's text. `external_account.sync_failed` is emitted when an account that worked fails and when it is switched off, not at every failed pull | An operator or the person must learn that a calendar stopped updating; an outage must not flood the subscribers of the event, and a client secret that expires must not make every person consent again. |
| Reconnecting while a pull runs | the lease of a pull is its fencing token: a reconnection clears it, and what the running pull then renewed or found is dropped instead of undoing the new connection (a pull with the old, revoked grant would otherwise switch the new connection off) | The person who connects again because the access was removed must not end up `disabled` by the pull of the old grant. |
| Disconnecting | `DELETE …/external-accounts/{id}` deletes the account and deletes its mirror calendar (soft, like any calendar: `retention.deleted_calendar_days`), then asks the provider to revoke the tokens (unless another account of the tenant holds the same grant, for example the same Google account connected for two people); a provider that cannot be reached does not keep the account. A deleted principal's accounts are switched off at the next pull and their access is given back | Disconnecting must work when the provider does not. |
| Secrets | the tokens are sealed with the secret sealer and bound to the tenant and the account; `admin rotate-keys` seals them again. Views, logs, events, metrics and audit records never carry a token, a code, a state or the provider's error text | `docs/operations/keys.md`. |

## Web pages: RSVP, feeds, OAuth callback, assets

| Topic | What Davhaven does | Why |
| --- | --- | --- |
| One answer for every bad token | an unknown, expired, revoked or wrong-surface RSVP or feed token, a suspended principal and a malformed token are the same 404 page. A rate limit is the one exception: it answers 429 with `Retry-After` | The page must not say which tokens exist. Hiding the 429 would make the limiter useless against guessing. |
| RSVP link tokens | derived from the key ring and the token row, not drawn at random (ADR-0007); the page hashes the secret component of the presented token | A mail that is composed again on every retry must carry the same link without storing a credential in the outbox. |
| RSVP `GET` | read-only, works without JavaScript, shows the summary, the time, the location and the organizer's name, answers `no-store` | Mail scanners and link previews fetch every link; fetching must not answer for the attendee. |
| RSVP `POST` | `application/x-www-form-urlencoded` with `partstat` (`ACCEPTED`, `DECLINED` or `TENTATIVE`), an optional `comment` of at most 500 characters and the `csrf` token of the page (bound to the RSVP token, valid for one hour). A field that appears twice is refused. Repeatable: an attendee can change their mind. A foreign `Origin` is refused before the handler runs | The answer changes state, so it needs the CSRF token and the same-origin check of PLAN 2.13. A repeated field must not slip past a check that reads the first occurrence. |
| Page headers | `Content-Security-Policy: default-src 'none'; style-src 'self'; img-src 'self'; font-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `X-Robots-Tag: noindex, nofollow`, `Cache-Control: no-store`, no cookies | The pages need no script and no third-party source; a token in the URL must not leak through the referrer, a cache or a search index. |
| Error pages | every failure of the web routes (an unknown, expired, revoked or cancelled link, a path or a method that does not exist, the backoff after failed tokens, a service that is not available) is the `rsvp_unavailable` page of the theme, worded by the status: 404 "this link is not valid", 429 "too many requests", 5xx "temporarily not available", any other 4xx "the request could not be processed". It is rendered in the theme the deployment chose (`templates.default_theme`) and in the first language of the visitor's `Accept-Language` that the theme ships (the renderer decides, so a theme with other languages is served in them), else in the deployment's default language (`templates.default_locale`); the pages that were rendered are kept per status and languages. It contains no path, token or message of the application. When the page cannot be rendered, or the failure happens in the edge layers before the routes (a body that is too large, a header that is too long, the request rate limit of the edge), a small static English page with the same status takes its place | An error page must not echo what an attacker chose. A link that does not authenticate has no tenant, and a page in the theme of one tenant for tokens that exist and another for tokens that do not would tell which are which, so a bad link looks like the rest of the deployment and the same for every cause. |
| Feeds | `GET /feeds/{token}.ics`: `text/calendar; charset=utf-8`, strong `ETag` and `304`, `Last-Modified`, `Cache-Control: private, max-age=300`. A name without `.ics` is a 404. Calendar access is checked on every request, so a revoked or unreadable calendar is a 404 | Subscribing clients poll; the strong validator makes polling cheap and the short private cache keeps revocation prompt. |
| OAuth callback | `GET /oauth/{provider}/callback` carries no credential: the single-use `state` (`{tenant}.{secret}`, so the right tenant is opened) names tenant, principal and provider, and the application consumes it before it does anything else. `code`, `state` and `error` are limited in size and may not repeat; the `code` is handled as a secret. The answer is the `oauth_result` page (a success or a failure page that says nothing of the reason, `200`) or the 404 of a state that is unknown, expired, used or of another provider | The browser returns from the provider without any session of ours, and a state cannot be tried twice. |
| Theme assets | `GET /assets/{theme}/{file}`: plain names only, a strong `ETag` and `304`, `Cache-Control: public, max-age=3600`; the files come from the application (ADR-0010) | The pages link their style sheet from the own origin because the policy allows no inline style. |
